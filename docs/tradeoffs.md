# 트레이드오프 & 의사결정 로그

주요 기술 선택의 대안·트레이드오프·결정 근거를 기록한다. 최신 항목이 위로 온다.

## TD-050. 내보내기 잠금: 복구 키로 봉인한 파일

- **결정일**: 2026-08-02
- **결정**: ✅ **복구 키로 AES-256-GCM 봉인 + 평문 CSV 경로 전면 제거 + 파일의 복구 키로만 열림**
- **상태**: 확정 (구현 완료)

CSV 내보내기가 비밀번호를 평문으로 남겨, 파일 하나가 새면 볼트 전체가 새는 것과 같았다.
경고 문구만으로는 부족해 파일 자체를 잠그기로 했다.

### 선행 검토 — 백업 기능과의 관계
암호화하면 이 앱에서만 열리므로, 이미 있는 **백업**(암호화 볼트 통째 복사)과 역할이 겹친다.
그럼에도 별도로 두는 이유는 성격이 다르기 때문이다:
백업은 *볼트 파일의 복제*(그 시점 마스터 비번으로 열림)이고, 잠긴 내보내기는 *항목 데이터의 사본*
(마스터 비번을 잊어도 복구 키만 있으면 열림)이다. 다른 볼트로 항목만 옮길 때도 쓸 수 있다.

### 선택지 1 — 무엇으로 잠글 것인가

| 선택지 | 트레이드오프 |
|---|---|
| A. 복구 키 *(채택)* | 관리할 비밀이 늘지 않고, 마스터 비번을 잊어도 열 수 있다. 종이·금고에 둔 키를 내보낼 때마다 꺼내야 함 |
| B. 마스터 비밀번호 | 외우고 있어 편하지만, 비번을 바꾸면 옛 파일은 옛 비번으로 열어야 해 헷갈림 |
| C. 내보낼 때 정하는 별도 암호 | 남에게 전달하기 좋으나 관리할 비밀이 하나 더 늘고, 잊으면 그 파일은 끝 |

### 선택지 2 — 평문 CSV 존치

처음엔 "둘 다 제공, 암호화가 기본"으로 갔다가, 잠긴 내보내기를 붙여놓고 보니 평문 카드가 남아 있을
이유가 없어 **전면 제거**로 다시 정했다. 그 과정에서 내보내기와 가져오기가 대칭이 아니라는 점이 드러났다:

- **평문 내보내기는 위험을 *만든다*** — 앱이 비밀번호를 평문으로 디스크에 새로 쓴다.
- **평문 가져오기는 위험을 만들지 않는다** — 읽기만 하며, 그 파일은 이미 사용자가 갖고 있던 것이다.

| 선택지 | 트레이드오프 |
|---|---|
| A. 둘 다 제거 *(채택)* | 설정이 가장 단순해지고 평문 경로가 사라짐. 초기 이관이 끝난 뒤라 밖에서 들여올 일이 없다는 판단 |
| B. 내보내기만 제거 | 위험을 만드는 쪽만 없애고 들여오는 길은 유지. 카드가 하나 더 남음 |
| C. 둘 다 유지, 암호화가 기본 | 이사할 길이 남지만 경고 문구에 기대는 평문 경로가 그대로 |

**감수하는 것**: 이 앱에서 다른 비밀번호 관리자로 옮길 방법이 없어진다(잠긴 파일은 이 앱 전용).
직접 만든 도구라 소스가 있고, `CsvVault`·`VaultManager.ExportCsv`는 그대로 남아 있어
필요하면 UI만 되살리면 된다는 점이 완충이다.

### 선택지 3 — 가져오기 판정 기준

| 선택지 | 트레이드오프 |
|---|---|
| A. 파일을 봉인한 복구 키로만 *(채택)* | 암호화의 자연스러운 성질. 재발급(TD-035) 후에도 옛 파일이 열리고, 다른 볼트로 옮기기도 가능 |
| B. 현재 볼트의 복구 키와 일치할 때만 | 사고 방지가 되지만 정상적인 옛 파일까지 못 여는 제약이 생김 |

### 결정 근거
- 복구 키는 이미 256-bit 고엔트로피 랜덤이라(`VaultService.RecoveryKeySizeBytes`) **KDF 없이 그대로**
  AES 키로 쓸 수 있다 — 볼트 헤더가 복구 래핑에 쓰는 방식과 같다(TD-010).
- **봉인 전 키 검증이 필수**다. 틀린 키로 잠그면 그 파일은 영영 열 수 없으므로,
  헤더의 `DekByRecovery`를 풀어보고(`VaultManager.VerifyRecoveryKey`) 맞을 때만 봉인한다.

### 구현 메모
- `EncryptedExport` — 파일 구조 `magic(8) + nonce(12) + tag(16) + ciphertext`. magic("PWMEXP01")을
  AEAD 연관 데이터로도 넣어 헤더 바꿔치기를 막고, 포맷 불일치는 `FormatException`,
  키 오류·변조는 `InvalidRecoveryKeyException`으로 구분해 던진다(사용자 안내 문구가 달라진다).
- `VaultManager.VerifyRecoveryKey` / `ExportEncrypted` / `ImportEncrypted` 추가.
- 복구 키 입력은 `IDialogService.PromptAsync`를 새로 두고, 셸의 기존 확인 오버레이에
  입력창 모드를 얹어 구현했다(별도 화면을 만들지 않음). 입력값은 창을 닫을 때 지운다.
- 확장자는 `.pmexport`. 이 포맷이 아닌 파일을 고르면 암호 문제가 아니라 형식 오류로 안내한다.
- 평문 경로 제거는 **UI와 커맨드만** 걷어낸 것이다. `CsvVault`와 `VaultManager.ExportCsv`/`ImportCsv`는
  잠긴 내보내기가 속으로 계속 쓰므로 그대로 남아 있고, 그 테스트도 유지된다.

## TD-049. 하위 화면에서 돌아왔을 때 목록 위치: 선택 항목으로 스크롤

- **결정일**: 2026-08-02
- **결정**: ✅ **선택 항목을 화면 안으로 스크롤 + 항목을 다룬 모든 복귀 경로에 적용**
- **상태**: 확정 (구현 완료)

OTP 게이트를 통과해 목록으로 돌아오면 스크롤이 맨 위로 튀어, 방금 인증한 계정을 다시 찾아
스크롤해야 했다. 셸이 `ContentControl.Content`를 갈아끼우는 구조(`ShellWindow.xaml`)라
게이트에 갔다 오면 `MainView`가 통째로 새로 만들어지고, 그 안의 `ScrollViewer`도 초기 상태로 돌아간다.

### 선택지 1 — 복원 방식

| 선택지 | 트레이드오프 |
|---|---|
| A. 선택 항목으로 스크롤 *(채택)* | 이미 있는 `SelectedEntry`를 그대로 활용. 선택 강조까지 켜져 어디였는지 명확하고, "최근 사용순" 정렬처럼 순서가 바뀌어도 정확히 그 항목을 찾아감 |
| B. 스크롤 오프셋 저장·복원 | 구현은 단순하나 인증 직후 `MarkUsed`로 순서가 바뀌면(최근 사용순) 엉뚱한 자리로 감. 항목 추가·삭제에도 어긋남 |
| C. A + B 폴백 | 빈틈은 없으나 상태 관리가 늘고, 실제로 B가 필요한 경우가 드묾 |

### 선택지 2 — 적용 범위

| 선택지 | 트레이드오프 |
|---|---|
| A. 항목을 다룬 모든 복귀 *(채택)* | 인증 통과·취소, 비밀번호 보기 닫기, 편집 저장·취소 전부 동일하게 동작 → 규칙이 하나라 예측 가능 |
| B. OTP 인증 통과 후만 | 요청 범위에는 맞지만 취소·편집 복귀는 여전히 맨 위로 튀어 같은 불편이 남음 |

### 결정 근거
- `_main`(MainViewModel)은 재사용되므로 **선택 상태는 이미 살아 있었다**. 실제로 사라지는 건 View의
  스크롤 위치뿐이라, 복원 로직을 셸의 복귀 경로마다 심을 필요 없이 View 한 곳에서 끝난다.
- 다만 편집 저장은 항목을 새 인스턴스로 교체하므로(TD-021) 참조 비교로는 선택이 풀렸다.
  `Refresh()`가 **id로 선택을 뒤쫓게** 고쳐, 범위 2-A가 코드 추가 없이 따라온다.

### 구현 메모
- `MainViewModel.Refresh()`: 선택 항목을 `filtered.Contains(참조)`가 아니라 `Id` 일치로 찾고,
  인스턴스가 바뀌었으면 새 것으로 갈아끼운다. 사라졌을 때 선택 해제·핀 해제 처리는 그대로.
- `MainView.MainView_Loaded`: 렌더 뒤(`DispatcherPriority.Loaded`)에 선택된 행을 찾아 `BringIntoView()`.
  이미 보이는 행이면 스크롤하지 않는다.
- `FindRow`는 즐겨찾기 그룹 여부까지 맞춰서 찾는다 — 핀한 계정은 양쪽 그룹에 같은 인스턴스로 나온다(TD-040).

## TD-048. 태그 칩 바 오른쪽 페이드: 넘칠 때만 표시

- **결정일**: 2026-08-02
- **결정**: ✅ **`ScrollableWidth > 0`일 때만 페이드 마스크 적용**
- **상태**: 확정 (구현 완료)

TD-030에서 가로 스크롤 어포던스로 넣은 오른쪽 페이드가 **조건 없이 항상** 걸려 있어,
태그가 두세 개뿐이라 넘치지도 않는데 마지막 칩이 흐리게 보였다. "흐림 = 옆에 더 있음"이라는
신호가 거짓이 되는 셈이다.

### 선택지 비교

| 선택지 | 트레이드오프 |
|---|---|
| A. 넘칠 때만 *(채택)* | 요청 그대로. 안 넘치면 선명. 다만 오른쪽 끝까지 스크롤한 상태에서는 여전히 흐림 |
| B. 넘치고 + 더 볼 게 있을 때만 | 신호가 항상 참이 되지만 스크롤 위치까지 추적해야 함 |
| C. 양쪽 반응(좌·우 페이드) | 어포던스가 가장 정확하나 그라데이션 계산이 복잡해짐 |

### 구현 메모
- 페이드 브러시를 `ScrollViewer.Resources`의 `TagFadeMask`로 옮기고, `ScrollChanged`에서
  `ScrollableWidth > 0`일 때만 `OpacityMask`에 걸어준다.
- 칩이 늘거나 창 폭이 바뀌면 extent/viewport가 달라지며 `ScrollChanged`가 다시 오므로,
  별도 `SizeChanged` 없이 한 곳에서 갱신된다.
- XAML `DataTrigger` 대신 code-behind를 택한 이유: `Style`을 새로 물리면 테마의 암시적
  `ScrollViewer` 스타일을 잃을 수 있고, `BasedOn`의 리소스 조회 실패는 런타임에야 드러난다.

## TD-047. 입력 중인 비밀번호 보기(👁): ui:PasswordBox 내장 버튼

- **결정일**: 2026-08-02
- **결정**: ✅ **A. `ui:PasswordBox`로 교체 + 새로 친 비번만 표시 + 수동 토글**
- **상태**: 확정 (구현 완료)

계정 생성 화면에서 비밀번호가 마스킹만 되어 있어, 방금 친 값이 맞는지 확인할 방법이 없었다.
생성기로 만든 비번을 사이트에 옮겨 적을 때도 눈으로 볼 수 있어야 한다.

### 선택지 1 — 컨트롤 방식

| 선택지 | 트레이드오프 |
|---|---|
| A. `ui:PasswordBox`로 교체 *(채택)* | WPF-UI 4.3의 `RevealButtonEnabled`가 칸 안에 눈 버튼을 내장 → 코드 최소, 다른 입력칸과 룩앤필 일관. 내부가 TextBox 파생이라 표시 중 평문이 텍스트 버퍼에 올라감 |
| B. 네이티브 `PasswordBox` + 별도 토글로 TextBox 스왑 | 숨김 상태에서 네이티브 컨트롤 특성 유지. 두 컨트롤 동기화·포커스 처리 코드가 늘어남 |
| C. 누르는 동안만 표시 | 어깨너머 노출이 가장 적으나 긴 비번 확인이 불편하고 마우스가 필요 |

### 선택지 2 — 편집 모드에서 기존 비번도 보여줄 것인가

| 선택지 | 트레이드오프 |
|---|---|
| A. 새로 친 것만 *(채택)* | 고정 10자리 자리표시(TD-026) 상태에서는 눈 버튼을 감춘다. 실제 길이를 감추는 취지가 유지됨 |
| B. 기존 비번도 표시 | 편집 폼은 이미 OTP 게이트(TD-025) 뒤라 정책 모순은 아니지만, TD-026이 사실상 무력화됨 |

### 선택지 3 — 자동 숨김

| 선택지 | 트레이드오프 |
|---|---|
| A. 수동 토글만 *(채택)* | 동작이 예측 가능하고 구현이 단순. 폼을 떠나면 어차피 사라짐 |
| B. 수십 초 뒤 자동 마스킹 | 클립보드 자동 삭제와 결이 같지만, 보면서 옮겨 적는 도중 꺼지면 거슬림 |

### 결정 근거
- 이미 WPF-UI를 쓰고 있어(TD-016) 내장 컨트롤이 가장 적은 코드로 일관된 UI를 준다.
- 평문 노출 범위는 **사용자가 방금 입력한 값**으로 한정된다. 저장된 기존 비번을 보는 경로는
  기존대로 목록의 OTP 게이트 보기 화면 하나로 유지 — 노출 경로를 늘리지 않는 게 핵심이다.

### 구현 메모
- `EntryEditView.xaml`: `PasswordBox` → `ui:PasswordBox RevealButtonEnabled="True"`.
- code-behind에 `HidePlaceholder()`를 두어 자리표시를 벗어나는 세 경로(포커스 진입·직접 입력·생성기)에서
  눈 버튼을 함께 되살리고, `ShowPlaceholder()`는 반대로 버튼을 감춘다.
- `PasswordInput.Clear()`는 `Password = string.Empty`로 바꿨다 — `ui:PasswordBox`에서 `Text`와
  `Password`는 별개 속성이라 TextBox의 `Clear()`에 의존하지 않는다.

## TD-046. 계정 추가 시 기존 사이트명 선택: 편집 가능 콤보박스

- **결정일**: 2026-08-02
- **결정**: ✅ **A. 편집 가능 콤보박스 + 가장 최근 수정 항목 기준 + 비어 있을 때만 채움**
- **상태**: 확정 (구현 완료)

같은 사이트에 계정을 하나 더 만들 때 사이트명·URL·태그를 매번 다시 치는 게 번거롭다.
평면 구조(TD-003)라 같은 사이트명 항목이 여럿 존재할 수 있고, 표기가 조금씩 달라지면
목록 그룹핑도 깨진다. 기존 값을 그대로 물려받는 경로가 필요했다.

### 선택지 1 — UI 형태

| 선택지 | 모습 | 트레이드오프 |
|---|---|---|
| A. 편집 가능 콤보박스 *(채택)* | 사이트명 칸 자체가 드롭다운 + 타이핑 가능 | 칸이 늘지 않고 "선택 or 직접입력"이 한 컨트롤에서 해결. WPF-UI 콤보의 편집 모드 스타일이 다른 입력칸과 미세하게 다를 수 있음 |
| B. 별도 선택 드롭다운 | 사이트명 위에 "불러오기" 드롭다운을 따로 둠 | 동작이 가장 명확하나 폼에 칸이 하나 늘고, 쓰지 않는 사용자에게도 항상 보임 |
| C. 라디오 토글 | "기존 선택 / 직접 입력" 모드 전환 | 의도는 명시적이나 클릭이 늘고 이 규모엔 과함 |

### 선택지 2 — 같은 사이트명이 여러 개일 때 출처

| 선택지 | 트레이드오프 |
|---|---|
| A. 가장 최근 수정 항목 *(채택)* | 최근에 손본 값이 가장 정확할 가능성이 높음. 기준이 하나라 결과가 예측 가능 |
| B. URL은 최근, 태그는 합집합 | 태그를 빠뜨릴 일은 없지만 무관한 태그가 딸려와 필터가 지저분해짐 |
| C. 가장 오래된(처음 만든) 항목 | 원본 기준으로 안정적이나, 그 뒤 바뀐 URL을 반영 못 함 |

### 선택지 3 — 이미 입력한 값이 있을 때

| 선택지 | 트레이드오프 |
|---|---|
| A. 비어 있을 때만 채움 *(채택)* | 사용자가 친 내용을 절대 지우지 않음. URL은 비었을 때만, 태그는 없는 것만 추가 |
| B. 항상 덮어쓰기 | 동작은 단순하나 입력하던 값이 예고 없이 사라짐 |
| C. 덮어쓰되 되돌리기 제공 | 안전하지만 선택 전 상태를 들고 있어야 해 복잡도 증가 |

### 결정 근거
- 사용자의 요구("드롭다운으로 선택, 없으면 직접 입력")를 컨트롤 하나로 그대로 표현하는 게 A.
- 자동 채움은 **편의 기능**이지 정답 주입이 아니다 → 사용자가 친 값을 이기지 않는 규칙(3-A)이 맞다.
- 태그 합집합(2-B)은 계정마다 태그를 달리 쓰는 경우 오염이 크다. 필요하면 선택 후 직접 더하면 된다.

### 구현 메모
- `EntryEditViewModel.KnownSites` — 폼을 열 때 활성 항목의 `Title`을 중복 제거(대소문자 무시)·이름순으로 스냅샷.
- `ApplySiteCommand(site)` — 해당 사이트명 항목 중 `UpdatedAt` 최신을 찾아 `Title`을 확정하고 URL·태그를 규칙대로 채운다. 목록에 없는 이름이면 아무것도 하지 않는다.
- `EntryEditView`는 `SelectionChanged`에서만 커맨드를 호출하고, 폼을 여는 중 발생하는 초기 선택은
  `_siteSelectionReady` 플래그로 무시한다(편집 모드에서 자기 사이트명이 자동 선택되며 태그가 딸려오는 것 방지).
- **후속(2026-08-02)**: `IsTextSearchEnabled="False"`로 인라인 자동완성을 껐다. 기본값(켜짐)에서는
  기존 사이트와 앞글자가 겹치는 새 이름을 칠 때 입력이 멋대로 완성되고, 그 선택이 `SelectionChanged`를
  일으켜 원하지 않은 URL·태그까지 딸려왔다. 이제 자동 채움은 **드롭다운에서 직접 고른 경우에만** 일어난다.

## TD-045. 배포 전 점검에서 고친 세 가지

- **결정일**: 2026-08-01
- **상태**: 확정 (구현 완료)

실사용 전 점검에서 나온 문제와 처리. 셋 다 "동작은 하지만 특정 조건에서 무너지는" 부류였다.

### ① 초기화 중 삭제 실패 시 앱이 죽던 문제

`OnResetRequested`는 이벤트 핸들러라 `async void`인데, `File.Delete`를 감싸는 예외 처리가 없었다.
**`async void`에서 새어 나온 예외는 잡히지 않아 프로세스가 그대로 종료된다.** 백신·탐색기가 파일을
잡고 있거나 권한이 없으면 실제로 발생한다.

- 파일마다 `try/catch`로 잡아 **실패 목록만 모으고 나머지는 계속 지운다**.
- **볼트 본체가 남았는지로 성패를 가른다**: 남았다면 초기화된 게 아니므로 생성 화면으로 넘기지 않고
  실패를 안내한다(넘겼다면 "지워졌다"는 거짓 신호를 주는 셈).
- 사이드카만 실패한 경우는 볼트가 사라졌으니 생성 화면으로 가되, 남은 파일을 함께 알린다.

### ② 즐겨찾기 항목이 두 곳에서 동시에 강조되던 문제

TD-040 조정으로 핀한 계정을 **양쪽 그룹에 모두** 표시하게 되면서 생긴 부작용이다.
두 그룹이 **같은 `VaultEntry` 인스턴스**를 공유하는데 선택 판정이 `ReferenceEquals`뿐이라,
↑↓로 이동하면 즐겨찾기 행과 사이트 그룹 행이 함께 켜졌다.

- `MainViewModel.SelectionInFavorites`를 두어 **"어느 그룹의 행을 골랐는지"까지** 선택 상태에 포함.
- 컨버터가 항목 일치 + 그룹 일치를 모두 볼 때만 강조한다.
- **키보드 이동은 항상 사이트 그룹 쪽을 고른다** — ↑↓는 중복 없는 평면 목록(`Entries`) 기준이라
  원래 자리에 강조를 주는 편이 일관적이다. 다만 **이동이 일어나지 않았다면(끝에서 정지) 그대로 둔다**.
- 마우스 클릭은 누른 행의 부모 `ItemsControl`에서 그룹을 찾아 그 그룹으로 선택한다.

### ③ 개발용 시드가 배포본에 포함되던 문제

`DevSeed`는 `PWM_SEED=1`일 때만 도는 개발 편의 코드지만 Release에도 그대로 컴파일됐다.
실제 볼트를 건드리진 않아도, 하드코딩된 시드 비밀번호와 개발 경로가 배포 exe에 남는다.

- `DevSeed.cs` 전체와 호출부를 **`#if DEBUG`로 감쌌다**. 게시본에는 이 경로가 아예 없다.
- 이미 공개 저장소 히스토리에 남은 시드 비밀번호는 **더미 볼트 전용**이라 실제 위험은 없다.

### 점검했으나 문제없던 것
잠금 시 `MainViewModel` 폐기(이전 세션 잔존 없음) · 초기화 후 로그인 잠금 자동 해제(`LoginThrottle`이
매번 파일에서 읽음) · CSV 내보내기의 휴지통 제외 · 삭제 시 즐겨찾기 자동 해제.

### 남겨둔 것 (수정 불필요로 판단)
- **OTP 인증마다 볼트가 저장된다** — `lastUsedAt` 기록 때문. 원자적 쓰기라 안전하고, 열람이 곧
  "사용 기록"이라는 설계상 의도된 쓰기다.
- **초기화 후에도 슬랙 설정 캐시가 메모리에 남는다** — 초기화 직후는 볼트 생성 화면이라 알림이
  발생할 경로가 없다.

## TD-044. 전체 데이터 초기화: 진입 경로와 방어 장치

- **결정일**: 2026-08-01
- **결정**: ✅ **언락 화면 비밀번호 칸에 `/reset` 입력** → 경고창 확인 → 볼트와 사이드카 전부 삭제
- **상태**: 확정 (구현 완료)

> 쉬운 말: 마스터 비밀번호도 복구 키도 잃었다면 볼트를 되살릴 방법이 없다. 그때 처음부터 다시 시작하려면
> 파일을 지워야 하는데, 지금까진 사용자가 `%APPDATA%`를 직접 찾아가야 했다.

### 배경 — 진입점이 잠금 해제 *이전*이어야 한다
초기화가 정작 필요한 상황은 **마스터 비밀번호와 복구 키를 둘 다 잃었을 때**다. 그런데 그때는 볼트를
열 수 없으므로 **설정 화면(S7)에 넣으면 닿을 수 없다**. 같은 이유로 "마스터 비밀번호 재확인"을 방어
장치로 쓸 수도 없다 — 그걸 몰라서 초기화하는 것이기 때문.

### 선택지 비교 — 진입 경로

| 선택지 | 트레이드오프 |
|---|---|
| A. 언락 화면 `/reset` 커맨드 *(채택)* | 버튼이 없어 실수로 누를 수 없고, 아는 사람만 실행한다. 발견성이 낮은 건 의도된 것 |
| B. 언락 화면 링크 | 발견하기 쉽지만 **되돌릴 수 없는 동작이 상시 클릭 가능**한 자리에 놓인다 |
| C. 명령줄 플래그(`--reset`) | 실수 여지가 가장 적으나 GUI 앱에서 명령 프롬프트를 요구해 실사용이 번거롭다 |
| D. 설정 화면 | **정작 필요한 순간에 접근 불가**(볼트를 못 엶) → 목적을 달성하지 못함 |

### 결정 근거
- A는 **"쉽게 누를 수 없게"라는 요구와 "잠금 전에 닿아야 한다"는 제약을 동시에** 만족한다.
- **커맨드가 실제 비밀번호와 충돌하지 않는다**: 마스터 비밀번호는 최소 12자(TD-009)인데 `/reset`은
  6자라, 누군가 이 문자열을 비밀번호로 설정하는 일 자체가 불가능하다. 우연한 오작동이 구조적으로 없다.
- 확인은 **경고창 1회**로 정했다. 커맨드를 직접 타이핑한 시점에서 이미 의도가 확인되므로,
  경고창에서 문구를 또 입력시키는 건 같은 확인을 두 번 받는 셈이다.

### 설계 결정
- **재시도 잠금(TD-024)보다 먼저 커맨드를 확인한다.** 비번을 여러 번 틀려 잠긴 상태야말로 초기화가
  필요한 순간인데, 잠금에 막혀 초기화조차 못 하면 곤란하다. 커맨드는 실패 횟수로도 세지 않는다.
- **사이드카까지 전부 지운다**: `vault.dat` · `.tmp` · `.bak` · `.lockout` · `slack-failures.log`.
  백업만 남기면 어차피 열 수 없는 파일이 남을 뿐이라 "첫 설치 상태로"라는 목적이 깨진다.
- 삭제 전에 `Lock()`으로 **메모리의 키·평문부터 버린다**(design 5.5).

### 구현 메모 — 인터페이스를 분리한 이유
파일 삭제를 `IVaultFileStore`에 얹으면 **구현체 16곳(대부분 테스트 스텁)을 전부 고쳐야** 한다.
초기화 하나 때문에 감당할 변경이 아니라서 이렇게 나눴다.
- **무엇을 지울지**: `VaultReset.PathsFor`(Core) — 파일 I/O가 없는 순수 함수라 규칙을 단위 테스트한다.
- **실제 삭제**: `IFileEraser`(ViewModels.Services) — 메서드 2개짜리 작은 인터페이스. 앱은 파일 시스템으로,
  테스트는 가짜 파일 시스템으로 구현해 초기화 흐름 전체를 검증한다.

## TD-043. 복구 키 복사: 클립보드 허용 여부

- **결정일**: 2026-08-01
- **결정**: ✅ **복사 버튼 제공**. 단 비밀번호와 동일하게 **클립보드 자동 삭제**를 건다
- **상태**: 확정 (구현 완료)

### 배경
복구 키는 화면에 한 번만 표시되고(최초 생성·재발급) 이후 다시 볼 수 없다. 그런데 손으로 옮겨 적는
방법밖에 없어, 26자 남짓한 키를 **오타 없이 옮기기 어렵다**. 오타 난 복구 키는 정작 필요한 순간에
쓸모가 없다 — 그런데 그 사실을 확인할 방법도 없다.

### 선택지 비교

| 선택지 | 트레이드오프 |
|---|---|
| A. 자동 삭제 붙인 복사 *(채택)* | 오타 없이 암호 관리자·메모에 옮길 수 있다. 클립보드에 잠깐 노출되지만 자동 삭제로 창을 좁힌다 |
| B. 복사 금지(현행) | 클립보드 경유 유출이 원천 차단. 대신 **손으로 옮겨 적다 틀릴 위험**을 사용자에게 떠넘긴다 |
| C. 파일로 내보내기 | 오타는 없으나 **평문 파일이 디스크에 남는다** — 복구 키의 의미가 크게 훼손(design 5.7) |

### 결정 근거
- **실제 위험은 "클립보드 유출"보다 "잘못 적은 복구 키"** 쪽이 크다고 봤다. 복구 키는 마스터 비밀번호를
  잊었을 때의 유일한 수단이라, 못 쓰는 복구 키는 사실상 복구 수단이 없는 것과 같다.
- 이미 비밀번호에 같은 판단을 적용해 **자동 삭제 붙인 복사**를 제공하고 있다(design 5.5·TD-027).
  더 중요한 비밀인 복구 키만 복사를 막는 것은 일관성이 없다.
- C(파일 내보내기)는 "앱은 복구 키를 평문으로 저장하지 않는다"(design 5.7)와 정면으로 충돌해 배제.

### 구현 메모
- `ClipboardCopier.Copy`(자동 삭제 없음, 아이디용)가 아니라 **`CopyWithAutoClear`** 를 쓴다.
  복구 키는 비밀이므로 아이디와 같은 취급을 하면 안 된다.
- 볼트 생성 화면에서는 아직 볼트가 없어 삭제 지연이 기본값(20초)이다. 재발급 화면은 설정값을 따른다.
- **여전히 오프라인(종이) 보관을 권한다** — 복사는 옮겨 적기의 대체가 아니라 정확도 보조다.
  화면 문구와 보관 확인 체크는 그대로 둔다.

## TD-042. 배포 형태: 단독 실행 exe vs 런타임 의존 exe

- **결정일**: 2026-08-01
- **결정**: ✅ **self-contained 단일 exe**(win-x64, 압축). `publish/PasswordManager.exe` 약 71MB
- **상태**: 확정 (v1.0.0 게시 완료)

### 배경
기능(M1~M6 + 편의 기능)은 끝났지만 **`dotnet run` 없이는 실행할 수 없는 상태**였다.
매일 쓰는 앱이 되려면 실행 파일 하나로 떨어져 시작 메뉴에 올라가야 한다.

### 선택지 비교

| 선택지 | 크기 | 트레이드오프 |
|---|---|---|
| A. self-contained 단일 exe *(채택)* | ~71MB | .NET 설치 불필요, 다른 PC·USB에 복사만 하면 동작. 런타임 버전 문제 없음. 용량 큼 |
| B. framework-dependent 단일 exe | ~5MB | 가볍지만 **.NET 8 Desktop Runtime**을 따로 설치해야 함 |

### 결정 근거
- **로컬 전용·무설치 기조(TD-001)와 결이 같다** — 볼트가 파일 하나이듯 앱도 파일 하나면 자기완결적이다.
- 개인 PC용이라 **71MB는 실질적 부담이 아니다**. 반대로 런타임 설치 안내는 실제 마찰이 된다.
- 나중에 다른 PC로 옮기거나 USB에 넣어 쓸 때 A가 그대로 동작한다.

### 구성 메모
- **RID·단일 파일 옵션은 csproj에 넣지 않고 publish 명령에서 준다.** csproj에 `RuntimeIdentifier`를
  박으면 일반 개발 빌드 산출물 경로까지 RID별로 갈라져 불편하다. 명령 전문은 README에 있다.
- `AssemblyName`을 `PasswordManager`로 바꿔 산출물이 `PasswordManager.exe`가 된다(이전엔 `PasswordManager.App.exe`).
- `-p:DebugType=none`으로 pdb를 빼 **exe 한 개만** 남긴다.
- **앱 아이콘**은 외부 이미지 도구 없이 `tools/make-icon.ps1`이 GDI+로 그려 `.ico`를 만든다
  (인디고 라운드 사각 + 흰 자물쇠, 16~256px 6종). 아이콘을 잃어도 재생성할 수 있다.
  - 이 스크립트는 **ASCII 주석만** 쓴다 — Windows PowerShell 5.1은 BOM 없는 UTF-8을 ANSI로 읽어
    한글 주석이 깨지고, 그 여파로 뒤따르는 줄까지 파싱이 어긋난다(실제로 겪은 문제).
- `publish/`는 `.gitignore` 대상 — 71MB 산출물을 저장소에 넣지 않고 명령으로 재생성한다.

## TD-041. 삭제 방식: 즉시 영구 삭제 vs 휴지통(소프트 삭제)

- **결정일**: 2026-08-01
- **결정**: ✅ **휴지통(소프트 삭제)**. `deletedAt`을 찍어 숨기고, **30일** 뒤 언락 시 자동 영구 삭제
- **상태**: 확정 (구현 완료)

> 쉬운 말: 삭제해도 바로 없애지 않고 휴지통에 30일 둔다. 그 안에는 되살릴 수 있고, 지나면 알아서 사라진다.

### 배경
기존 `Remove`는 `Entries.RemoveAll`로 **즉시 영구 삭제**였다. 확인 다이얼로그가 유일한 방어선이라,
잘못 누르면 비밀번호 이력까지 통째로 사라진다 — 복구 수단이 전혀 없었다.

### 선택지 비교 — 보관 정책

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 30일 자동 삭제 *(채택)* | `deletedAt` + 언락 시 만료분 정리 | 볼트가 무한정 커지지 않고, 되살릴 시간도 충분. 날짜 계산이 필요 |
| B. 개수 상한 20개 | 오래된 것부터 밀어냄 | 기간 계산이 없어 가장 단순(`passwordHistory`와 같은 방식). 며칠이 지나야 사라지는지 예측 불가 |
| C. 무기한 보관 | 수동 비우기만 | 절대 안 잃지만 볼트 크기·정리 부담이 사용자 몫 |

### 결정 근거
- **"실수 삭제 되돌리기"가 목적**이라 되살릴 시간(30일)만 보장되면 충분하고, 그 뒤엔 남길 이유가 없다.
- B(개수 상한)는 단순하지만 **"언제 사라지는지"를 사용자가 알 수 없어** 휴지통의 안심 효과가 약하다.
- 정리 시점을 **언락 시**로 잡았다 — 백그라운드 타이머가 필요 없고, 볼트가 열린 순간은 어차피 저장이 일어나는 때다.

### 설계 결정
- **`Entries`는 활성 항목만** 돌려준다(`DeletedAt is null`). 기존 호출부(목록·검색·CSV 내보내기)는
  코드를 고치지 않아도 휴지통 항목을 자동으로 제외한다 — 소프트 삭제 도입의 핵심 안전장치.
- **`Get(id)`도 휴지통 항목을 반환하지 않는다.** 복원 전까지는 없는 것처럼 다뤄야 하기 때문.
- **삭제 시 `IsPinned`를 끈다.** 휴지통 항목이 즐겨찾기 그룹에 남아 있으면 안 된다.
- **경계 처리**: 정확히 30일째는 남기고 **초과분만** 지운다(`deletedAt < now - 30일`).
- **복원·영구삭제에 OTP 게이트를 두지 않는다** — 둘 다 비밀번호를 노출하지 않아 TD-032의 범위 밖이다.
  대신 **되돌릴 수 없는 동작(영구삭제·비우기)만** 확인 다이얼로그를 받는다.
- **UI 위치는 설정 > 백업·데이터**. 사이드바를 늘리지 않으면서, design 7.9의 "설정은 새 부가 기능의
  편입 지점" 방침을 따른다. 버튼에 보관 개수를 함께 띄워 발견성을 보완한다.

## TD-040. 즐겨찾기와 정렬: 항목이 늘어날 때의 탐색 비용

- **결정일**: 2026-08-01
- **결정**: ✅ **계정 단위 핀 + 전용 "즐겨찾기" 그룹** / **정렬 3종(이름·최근 변경·최근 사용), 볼트에 저장**
- **상태**: 확정 (구현 완료)

### 선택지 비교 — 핀 단위

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 계정 핀 + 전용 그룹 *(채택)* | 핀한 계정을 맨 위 "즐겨찾기" 그룹으로 모음 | 규칙이 명확하고 구현 단순 |
| B. 계정 핀 + 그룹 끌어올림 | 핀한 계정이 속한 사이트 그룹이 위로 | 사이트 문맥 유지. "왜 이 그룹이 위에 있지?"가 덜 직관적 |
| C. 사이트 그룹 단위 핀 | 사이트 전체를 고정 | 가장 단순하나 **"같은 사이트의 주계정만 고정"이 불가** → TD-003(한 사이트 여러 계정)과 상충 |

### 결정 근거
- 이 앱의 핵심 시나리오가 **한 사이트에 여러 계정**(TD-003)이라, 고정 단위도 계정이어야 한다 → C 배제.
- A는 "핀한 것은 맨 위 한 곳에 모인다"는 규칙이 한 문장으로 설명돼 B보다 예측 가능하다.

> **실물 확인 후 조정(2026-08-01)**: 처음엔 중복 노출을 피하려 **핀한 계정을 원래 사이트 그룹에서 뺐는데**,
> 두 가지가 문제였다. ⑴ 즐겨찾기에 넣었더니 계정이 원래 자리에서 **사라진 것처럼 보인다**.
> ⑵ 즐겨찾기 그룹은 사이트가 아니라서 **행에 사이트명이 없어** 어떤 서비스인지 알 수 없다.
> → **즐겨찾기는 "바로가기"로 규정**하고 원래 사이트 그룹에도 그대로 남긴다. 대신 **즐겨찾기 그룹의
> 행에만 사이트명을 굵게 앞에 붙인다**(`Steam · main@…`). 같은 계정이 두 곳에 보이지만 별이 채워져 있어
> 이유가 읽히고, 어느 쪽을 눌러도 같은 항목이라 동작은 동일하다.

### 정렬 — 기준과 저장

| 기준 | 정렬 규칙 |
|---|---|
| **이름순**(기본) | 사이트명 → 아이디, 대소문자 무시 |
| **최근 변경순** | `lastChangedAt` 내림차순 |
| **최근 사용순** | `lastUsedAt` 내림차순, **한 번도 안 쓴 항목은 맨 뒤** |

- **기본값은 이름순**. "최근 사용순"은 쓸 때마다 목록이 재배열돼 **항목 위치를 외울 수 없다** — 기본으로
  두기엔 부담이 커서 선택지로만 제공한다.
- **정렬 기준은 볼트에 저장**(`sortOrder`)해 다음 실행에도 유지된다.
- **정렬은 계정과 그룹 모두에 적용**된다. 그룹 순서는 정렬된 계정 순서를 그대로 이어받으므로,
  같은 사이트 안의 계정끼리도 같은 기준으로 줄 선다.
- **즐겨찾기 그룹은 정렬과 무관하게 항상 맨 위**. 고정의 목적이 "위치 예측 가능성"이기 때문.

### `lastUsedAt`을 언제 찍을 것인가

**OTP 인증을 통과한 시점**으로 정했다(열람 게이트·편집 게이트 모두). 그 순간이 "실제로 이 계정을
쓰려는 순간"이라 노이즈가 가장 적다. 목록 클릭이나 아이디 복사만으로는 갱신하지 않는다 —
스크롤하다 눌러본 것까지 "사용"으로 치면 최근 사용순이 금세 무의미해진다.

### 구현 메모
- **`Update`가 앱 소유 필드를 이어받게 했다.** 편집 화면은 폼 값으로 **새 `VaultEntry`를 만들어**
  넘기므로(`EntryEditViewModel`), `IsPinned`·`LastUsedAt`·`DeletedAt`을 기존 항목에서 복사하지 않으면
  **편집할 때마다 즐겨찾기가 조용히 풀리고 휴지통 항목이 되살아난다**. `CreatedAt`·`PasswordHistory`가
  이미 같은 방식으로 보호되고 있었다(TD-021).
- 핀 토글은 OTP 게이트를 거치지 않는다 — 비밀 노출이 아니다(TD-032 범위 밖).

## TD-039. 키보드 단축키 세트와 목록 "선택" 개념 도입

- **결정일**: 2026-08-01
- **결정**: ✅ **기본 세트 7개** + 목록에 **선택 상태 도입**(옅은 배경 하이라이트로 표시)
- **상태**: 확정 (구현 완료)

### 배경 — 선택 개념이 없었다
계정 목록은 `ItemsControl`이라 **선택 행이라는 개념 자체가 없었다**. `MainViewModel.SelectedEntry`는
존재했지만 XAML 어디에서도 바인딩되지 않아 **항상 null**이었고, 모든 액션은 행 버튼이
`CommandParameter="{Binding}"`로 자기 항목을 직접 넘기는 구조였다.
그런데 ↑/↓·Enter·Ctrl+B는 "지금 선택된 행"이 있어야만 성립한다 → 선택 상태를 먼저 도입해야 했다.

### 선택지 비교 — 선택 표시 방식

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 사이드바와 같은 패턴 *(채택 후 조정)* | 좌측 강조 바(3×16) + 옅은 배경 | 앱 전체 시각 언어가 하나로 유지됨. 3.1절 자산 재사용 |
| B. 행 테두리 강조 | 선택 행에 강조색 outline | 더 뚜렷하나 카드(`CardBorderStyle`) 테두리와 중첩돼 산만 |
| C. 선택 개념 없이 진행 | ↑↓·Enter·Ctrl+B 포기, 4개만 | UI 변경 0이지만 목록 탐색이 계속 마우스 전용 |

> **실물 확인 후 조정(2026-08-01)**: A로 구현해 띄워 보니 **좌측 바는 계정 행에서 산만했다**.
> 사이드바는 항목 4개가 넉넉한 간격으로 놓이지만, 계정 행은 카드 안에 촘촘히 쌓여 세로 바가 겹쳐 보인다.
> → **좌측 바를 빼고 옅은 배경 하이라이트만** 남긴다. 강조 바는 사이드바 전용 표현으로 둔다.

### 채택한 단축키 (기본 세트)

| 키 | 동작 | 배선 |
|---|---|---|
| `Ctrl+F` | 검색창 포커스 + 기존 검색어 전체 선택 | `ApplicationCommands.Find` → 코드비하인드(포커스는 뷰의 몫) |
| `Ctrl+N` | 새 계정 | `NewEntryCommand` |
| `Ctrl+L` | 즉시 잠금 | `LockCommand` |
| `Ctrl+B` | 선택 항목 아이디 복사 | `CopySelectedLoginCommand` (KeePass 관례) |
| `Esc` | 검색어 + 태그 필터 해제 | `ClearFiltersCommand` |
| `↑` / `↓` | 선택 이동 (양끝에서 정지, 순환 없음) | `SelectPreviousCommand` / `SelectNextCommand` |
| `Enter` | 선택 항목 인증(OTP 게이트) | `VerifyCommand` (인자 null → `SelectedEntry` 폴백) |

- **확장 세트 보류**: `Ctrl+E`(편집)·`Delete`(삭제)·`Ctrl+,`(설정)·`F1`·`Ctrl+1..9`(태그)는
  오버레이·편집 화면과의 키 충돌 정리 부담이 커 이번 범위에서 제외.
- **비밀번호 복사 단축키는 두지 않는다** — 열람은 OTP 게이트를 거쳐야 하므로(TD-004·TD-032)
  단축키 한 방에 복사되면 게이트의 의미가 사라진다. 아이디(비밀 아님)만 `Ctrl+B`로 연다(TD-027 연장).

### 구현 메모 (실제로 걸렸던 지점)
- **선택 이동 기준은 `Entries`(필터 적용된 평면 목록)** — 화면에 안 보이는 항목으로 선택이 새지 않는다.
- **`Refresh()`가 선택을 정리한다**: 필터·삭제로 사라진 항목이 선택된 채 남으면 단축키가
  보이지 않는 행을 건드리므로, 목록 재구성 후 `filtered`에 없으면 `SelectedEntry = null`.
  이 책임을 한곳에 모으면서 `DeleteAsync`의 중복 해제 코드는 제거했다.
- **`UserControl.InputBindings`는 포커스가 그 화면 안에 있어야 발동**한다. 그래서 `Loaded`에서
  검색창에 포커스를 준다 — 바로 타이핑되는 편의이자 단축키가 먹기 위한 전제다.
- 확인 오버레이(`ConfirmOverlay`)가 떠 있을 땐 포커스가 오버레이에 트랩되므로 이 단축키들은 발동하지 않는다.

### 후속 조치 — 메뉴얼 재구성
단축키를 실을 자리를 만들면서 메뉴얼 화면의 틀도 함께 바꿨다.
- **주제별 섹션 카드**(시작하기 · 매일 쓰기 · 보안·복구) + **단축키 카드**(키칩 배지).
  단일 카드에 6줄을 몰아넣던 구조로는 단축키 7줄을 더 얹을 자리가 없었다.
- **문구를 `ManualViewModel`의 데이터로 이전**(`Sections`·`Shortcuts`). 항목마다 같은
  `Grid`+`ColumnDefinitions`를 복붙하던 100여 줄이 템플릿 2개로 줄고, 항목 추가가 한 줄이 됐다.
  "정적 내용이라 View가 담는다"던 기존 방침은 항목 수가 늘면서 뒤집었다.
- 아이콘은 문자열 이름으로 지정하고 `SymbolNameConverter`가 `SymbolRegular`로 변환한다 —
  ViewModel 계층이 WPF-UI에 의존하지 않게 하려는 것. 모르는 이름은 `Empty`로 떨어뜨려 렌더링이 깨지지 않는다.

## TD-038. "대강 완료" 이후 추가할 편의 기능 우선순위

- **결정일**: 2026-08-01
- **결정**: ✅ **A(단축키) → B(즐겨찾기·정렬) → C(휴지통)** 순으로 진행. D~F는 보류
- **상태**: 확정 (A 완료, B·C 예정)

### 배경
핵심 기능(M1~M6)이 마무리된 뒤, **보안이 아닌 편의** 축으로 무엇을 더할지 정리가 필요했다.

### 선택지 비교

| 후보 | 얻는 것 | 비용/리스크 | 판정 |
|---|---|---|---|
| A. 키보드 단축키 + 목록 조작 | 매일 쓰는 동선이 마우스 없이 끝남 | 낮음(모델 무관, 마이그레이션 0) | ✅ 채택 |
| B. 즐겨찾기(핀) + 정렬 옵션 | 항목이 늘수록 탐색 시간 급감 | 중(스키마 v3 필요) | ✅ 채택 |
| C. 휴지통(삭제 복구) | 실수 삭제 되돌리기 | 중(스키마 v3 + 복원 UI) | ✅ 채택 |
| D. URL 열기 + 항목 복제 | 부계정 등록이 몇 초 | 아주 낮음 | ⏸ 보류 |
| E. 트레이 상주 + 전역 핫키 | 어디서든 호출 | 중~높음(창 생명주기·자동잠금·단일 인스턴스와 얽힘) | ⏸ 보류 |
| F. 빠른 실행 팔레트(Ctrl+K) | 검색→복사가 한 흐름 | 중(A가 선행돼야 의미) | ⏸ 보류 |

### 결정 근거
- **A를 먼저**: 데이터 모델을 건드리지 않아 마이그레이션 부담이 0이고, 비용 대비 체감이 가장 크다.
- **B·C를 한 묶음으로**: 둘 다 `VaultEntry` 필드 추가가 필요하다. 이왕 스키마 버전을 올릴 거면
  `isPinned`·`lastUsedAt`·`deletedAt`을 **한 번에 v3로** 올리는 편이 마이그레이션 단계를 아낀다(TD-008).
- **E를 마지막으로**: 단일 인스턴스(TD-007)·자동 잠금·`ShellViewModel` 화면 전환과 상호작용이 많아
  기존 보안 동작을 흔들 위험이 가장 크다.

### 세부 결정 (B·C 착수 전 확정)
- **핀 단위**: 계정 단위로 핀하고, 핀한 계정은 목록 최상단 **"⭐ 즐겨찾기" 전용 그룹**에 모아 표시
  (원래 사이트 그룹에서는 빠짐). 그룹 단위 핀은 "같은 사이트의 주계정만 고정"이 안 돼 배제 — 이 앱의
  한 사이트 여러 계정 시나리오(TD-003)와 맞지 않는다.
- **`lastUsedAt` 갱신 시점**: **OTP 인증 통과 시**. 그 순간이 "실제로 이 계정을 쓰려는 순간"이라
  노이즈가 가장 적다. 목록 클릭·아이디 복사만으로는 갱신하지 않는다.
- **휴지통 보관**: **30일 자동 삭제**(언락 시 정리) + 수동 "휴지통 비우기". 볼트가 무한정 커지지 않는다.
- **휴지통 복원·영구삭제에는 OTP 게이트를 두지 않는다** — 둘 다 비밀번호를 노출하지 않는다(TD-032 범위 밖).

### 후속 조치
- A: `design-ux.md` 5절(키보드 단축키) 신설, 상세 결정은 TD-039.
- B·C: 스키마 v3 + `VaultMigrator` v2→v3 단계 추가. 착수 시 별도 TD로 기록.

## TD-037. 로그인 실패 슬랙 알림: 세션 메모리 캐시로 잠긴 상태 알림

- **결정일**: 2026-07-31
- **결정**: ✅ **세션 메모리 캐시(A안)**. 잠금 해제 시 슬랙 설정 스냅샷을 프로세스 메모리(`SlackConfigCache`)에 담아, 이후 볼트가 잠겨도 마지막 스냅샷으로 "로그인 실패" 알림을 보낸다
- **상태**: 확정

> 쉬운 말: Webhook 주소는 볼트 안(암호화)에 있어 잠긴 상태에선 못 읽는다. 그래서 한 번 열 때 설정을 메모리에 기억해 두고, 자리를 비운 사이 남이 틀린 비번을 넣으면 그 기억으로 알림을 보낸다.

### 배경 — 구조적 제약
Webhook URL은 볼트 내 암호화 저장(TD-012)이라 **잠긴 상태에선 설정 자체를 읽을 수 없다**. 그런데 "로그인 실패"는 잠긴 상태에서 발생 → 딜레마.

### 선택지 비교

| 선택 | 방식 | 트레이드오프 |
|---|---|---|
| A. 세션 메모리 캐시 *(채택)* | 잠금 해제 때 설정 스냅샷을 메모리에 보관 → 잠긴 뒤에도 그 값으로 알림 | 목적("자리 비운 사이 무단 접근 탐지")에 부합. 콜드 스타트 후 첫 해제 전엔 알림 불가. URL이 메모리 상주 |
| B. 로그인 실패 제외 | 잠금 해제·비번 변경만 알림 | 단순·안전하나 design 7.8 이벤트 하나 포기 |
| C. URL 볼트 밖 저장 | 평문/DPAPI로 볼트 밖 저장 | 잠긴 상태 알림 가능하나 **TD-012 위배** |

### 결정 근거
- 슬랙 알림의 본래 목적이 "무단 접근 탐지"라, 한 번이라도 정상 사용한 세션의 캐시로 실패를 알리는 게 목적에 가장 부합.
- C(볼트 밖 저장)는 "URL 볼트 내 암호화" 원칙을 깨므로 배제. B는 기능 축소.
- 콜드 스타트 사각지대(첫 해제 전 실패는 알림 불가)는 수용 — 그 시점엔 앱이 한 번도 열리지 않아 캐시가 없다.

### 후속 조치
- `SlackConfigCache`(Core): `Current` 스냅샷 보관. 잠금 해제·설정 저장 시 `Update`.
- `ShellViewModel`: 잠금 해제 시 캐시 갱신 + `Unlock` 알림, `UnlockViewModel.LoginFailed` 구독 → `LoginFailure` 알림, 에디터 저장 시 비번 변경분만 `PasswordChange`(제목=사이트명) 알림.
- 조립부(App): `SlackNotifier(() => cache.Current, HttpWebhookClient)`를 셸에 주입. 설정 OFF·미해제면 통신 0.

## TD-036. 웹캠 QR 스캔(M6 선택 기능): 미채택

> 쉬운 말: 사이트 2FA를 등록할 때 카메라로 QR을 찍어 읽는 기능은 넣지 않는다. 대신 `otpauth://...` 주소를 복사해 붙여넣는다.

### 선택지 비교

| 방식 | 동작 | 트레이드오프 |
|---|---|---|
| A. 웹캠 QR 스캔 | ZXing.Net + OpenCvSharp로 카메라 QR 디코드 | 편의↑. 그러나 **네이티브 카메라 라이브러리 2종 의존성** + 권한·디바이스 처리 복잡. TD-001 "의존성 최소화"와 정면 상충 |

### 후속 조치
- `design.md` 5.4(사이트별 OTP)·9(기술 스택)·11(M6 로드맵)에서 웹캠 스캔 항목을 미채택으로 표기.

| B. 행별 인증 게이트 *(채택)* | 인증 전 인증 버튼만, 후 3버튼 | 삭제까지 보호·UI 단순. OTP 미등록 시 아무 작업 불가(절벽) |

### 결정 근거
- 삭제는 되돌릴 수 없는 파괴적 동작 → 열람·편집과 동일하게 **OTP 문지기**로 보호(TD-004 연장).

### 후속 조치
- `OtpGatePurpose.Verify`, `MainViewModel.VerifyCommand`/`VerifyRequested`, `ShellViewModel.OnVerifyRequested`.
- `MainView.xaml` 행 액션을 `EntryVerifiedConverter`로 인증 전/후 전환.
- **미해결 리스크**: OTP 미등록 볼트는 보기·편집·삭제가 전부 막힘 → 최초 설정 흐름에서 OTP 등록 유도 필요(후속 검토).

## TD-029. 태그 다중선택 필터: OR(합집합) vs AND(교집합)

- **결정일**: 2026-07-31
- **결정**: ✅ **OR(합집합)** — 고른 태그 중 하나라도 달린 항목을 모두 표시
- **상태**: 확정

> 쉬운 말: 태그를 여러 개 고르면 "이거 아니면 저거"로 넓게 보여준다. `업무`+`쇼핑`을 고르면 업무 것과 쇼핑 것을 전부 보여준다(하나라도 달렸으면 표시).

### 배경
`VaultEntry.Tags`는 항목마다 여러 개 붙는 목록인데, 태그를 2개 이상 선택했을 때 좁힐지(AND) 넓힐지(OR)를 정해야 한다. 현재 `MainViewModel`엔 태그 필터가 없다(검색은 제목·로그인만).

### 선택지 비교

| 기준 | A. OR 합집합 *(채택)* | B. AND 교집합 | C. UI 토글(둘 다) |
|---|---|---|---|
| 직관성(개인용) | ⭐ "이거 아니면 저거" 자연스러움 | 처음엔 "왜 사라지지?" 헷갈림 | 유연하나 개념 노출 |
| 많은 항목 좁히기 | 약함(오히려 늘어남) | ⭐ 강력 | ⭐ 둘 다 |
| 구현 복잡도 | ⭐ 최소 | ⭐ 최소 | 토글 상태·UI 추가 |
| 이 앱 규모(수십~수백) | 적합 | 과할 수 있음 | 지금은 과함 |

### 결정 근거
- 개인용·항목 수가 적어 "좁히기"보다 **여러 분류를 한눈에 보기**가 더 흔하다.
- 좁히기는 이미 **검색창**으로 가능하므로 태그 필터는 넓히는 역할에 집중.
- 구현이 단순하고, 나중에 항목이 많아지면 **C(토글)로 확장** 가능.

### 후속 조치
- `MainViewModel`에 선택 태그 집합 + OR 필터(기존 검색어와 **AND 결합**: "검색어에도 맞고 + 태그 중 하나 이상") 구현.
- 검색어·태그 동시 적용 순서와 좁은 창 태그 pane 접힘은 구현 시 이어서 정리.

## TD-028. 언락 시 볼트 손상: 재시도 실패로 셀지 여부

- **결정일**: 2026-07-31
- **결정**: ✅ **손상은 비번 시도 실패로 세지 않고**, 비번 오류와 **구분되는 복구 안내**를 표시(세션은 열지 않음)
- **상태**: 확정

> 쉬운 말: "비번을 틀린 것"과 "파일이 부서진 것"은 다른 문제다. 파일이 부서졌는데 시도 횟수를 깎아 잠가버리면, 사용자는 백업으로 복원할 기회도 잃는다.

### 배경
Core는 이미 **비번 오류(`InvalidMasterPasswordException`)와 파일 손상(`VaultCorruptedException`)을 구분**한다(design 5.3·12). 그러나 `UnlockViewModel`은 비번 오류만 잡아, 손상 시 예외가 처리되지 않고 **앱이 죽을 수 있었다**(S9 미완).

### 선택지 비교

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 손상=실패로 카운트 | 손상도 재시도 제한(throttle)에 반영 | 부서진 파일을 여러 번 열려다 잠금 → 복원 기회까지 차단. 의미 없는 잠금 |
| B. 손상은 카운트 안 함 *(채택)* | throttle 미반영, 잠긴 상태 유지 + 복구 안내 | 손상 상태로 무한 재시도 가능하나 어차피 비번과 무관 → 실익 없음. 안내가 정답 |

### 결정 근거
- 재시도 제한(TD-024)은 **비번 무차별 대입을 늦추기 위한 것** → 파일 손상은 대입과 무관하므로 카운트 대상이 아니다.
- 손상은 사용자 잘못이 아니므로 **잠금으로 벌하지 않고**, **자동 백업(`vault.dat.bak`) 복원**이라는 다음 행동을 안내하는 게 옳다.

### 채택에 따른 후속 조치
- `UnlockViewModel.UnlockAsync`에 `VaultCorruptedException` catch 추가(TDD Red→Green).
- 후속: 언락 화면에 **"백업에서 복원" CTA**(잠금 상태 복원 흐름) 검토 — 현재는 텍스트 안내만.

## TD-025. 편집 게이트 통합과 세션 그레이스: 편집도 OTP + 한 번 통과 시 공유

- **결정일**: 2026-07-30
- **결정**: ✅ **편집도 열람과 동일하게 OTP 게이트. 한 항목에서 한 번 통과하면 그 항목의 보기·편집을 잠글 때까지 코드 없이 허용(그레이스). OTP 미등록 시 편집도 차단**

> 쉬운 말: 편집 화면도 기존 비번을 보여주므로 "보기"처럼 OTP를 요구한다. 대신 한 항목에서 보기든 편집이든 한 번 OTP를 통과하면, 그 항목의 나머지 동작은 볼트가 잠길 때까지 다시 묻지 않는다.

### 선택지 비교 — 그레이스 범위

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 잠금 시까지 *(채택)* | 통과한 항목을 세션 동안 기억, 잠금 시 해제 | 자연스럽고 덜 귀찮음. 자리비움은 자동잠금이 방어 |
| B. 현재 흐름만 | 보기↔편집 즉시 연결에만 유효 | 가장 엄격하나 목록 오갈 때마다 재인증 |
| C. 짧은 타이머 | 마지막 접근 후 N초 | 절충이나 구현·설명 복잡 |

### 선택지 비교 — OTP 미등록 시 편집

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 차단 *(채택)* | 보기와 대칭으로 "먼저 OTP 등록" 안내 | 보기·편집 일관. 미등록 볼트는 편집 불가(등록 유도) |
| B. 허용 | OTP 없으면 편집 자유 | 게이트가 반쪽. 편집으로 비번 노출 우회 가능 |

### 결정 근거

- 그레이스는 세션 범위(`ShellViewModel`의 통과 항목 집합)로 두고 잠금 시 비운다. 자리비움 위험은 자동잠금(TD-024 아님, design 5.5)이 상쇄.
- 미등록 편집을 열어두면 게이트를 우회하는 셈이라 보기와 대칭으로 차단.

- **결정**: ✅ **연속 5회 실패마다 잠금, 잠금 시간 지수 증가(1→5→30분, 이후 유지). 상태는 볼트 옆 사이드카 파일에 저장. 성공 시 리셋. 볼트 자동 폐기는 하지 않음**
- **상태**: 확정

> 쉬운 말: 이 재시도 제한은 "앱 화면으로 비번을 찍어보는 사람"만 막는 과속방지턱이다. 볼트 파일을 통째로 가져간 공격자는 앱을 거치지 않고 오프라인으로 대입할 수 있어 이 카운터가 무의미하다 — 그쪽 방어는 KDF(Argon2) 비용이 담당한다.

### 선택지 비교

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 도입 안 함 | KDF 비용에만 의존 | 오프라인 방어는 이게 본질이나, 눈앞의 찍기 공격엔 무방비 |
| B. 고정 5회/5분·메모리 | 카운터를 메모리에만 | 단순하나 앱 재시작으로 즉시 리셋(우회) |
| C. 지수 백오프 + 파일 저장 *(채택)* | 5회마다 1→5→30분, 사이드카 파일에 상태 저장 | 재시작 우회 차단 + 지연 누증. 사이드카 파일 삭제로는 리셋 가능(수용) |
| D. N회 후 볼트 폐기 | 아이폰식 자동 삭제 | 강력하나 데이터 영구 손실·악의적 잠금 위험(개인용엔 과함) |

### 결정 근거
- 위협 모델을 정직히 규정: 앱 UI 찍기 공격을 막는 **속도 저하 장치**이지 오프라인 브루트포스 방어가 아니다. 후자는 KDF(TD-015)가 담당.
- 메모리 카운터(B)는 재시작 한 번으로 무력화되므로, 최소한 파일 저장이 있어야 의미가 있어 채택.
- 지수 백오프로 고정 5분보다 끈질기게 지연. 사이드카 파일을 지우면 리셋되지만, 이는 파일 접근이 가능한 공격자(이미 오프라인 대입이 가능해 카운터가 무의미한 대상)에 한정되므로 수용.
- 볼트 폐기(D)는 잊어버린 비번·타인의 악의적 반복 실패로 인한 **데이터 손실 위험**이 커, 복구 키(TD-010)가 있어도 개인용 로컬 앱엔 부적합해 제외.

### 후속 조치
- 상태 저장: 암호화 본문 밖 사이드카(`<vault>.lockout`) — 잠긴 상태에서도 읽어야 하므로.
- "정말 세게"가 필요하면 별도로 **KDF 비용 상향**(TD-015/TD-022 계열)에서 다룬다.

## TD-023. 디자인 리모델링 범위·네비게이션 구조

- **결정일**: 2026-07-30
- **결정**: ✅ **네비게이션 재설계(왼쪽 사이드바 레일) + 카드 리스트 + 강조색 인디고(#6366F1)**
- **상태**: 확정 (상세 스펙은 `design-ux.md`)

> 쉬운 말: 화면을 통째로 바꿔치던 방식 위에 **왼쪽 사이드바**를 얹어 항목/설정/정보를 나누고,
> 항목은 표 대신 **카드**로 보여준다. 강조색은 쨍한 시안 대신 차분한 **인디고**.

### 배경
기능 완료 후 앱을 실제로 띄워보니 (1) 셸은 다크인데 클래식 `ListView`/`GridView`가

### 대안
- **A. 최소 버그픽스**: 목록만 다크 통일 + 버튼 색 조정. 빠르지만 인상 개선 작음.
- **B. 일관 폴리싱**: 토큰 정비 + 전 화면 통일. 중간 노력.
- **C. 네비게이션 재설계**: 사이드바 도입으로 구조까지 개편. 노력 크나 설정 화면(S7) 토대까지 확보.

### 결정 근거
- 사이드바는 툴바 난립을 해소하고, M6 3단계 **설정 화면(S7, design 7.9)** 을 자연스럽게 담는 그릇이 된다.
- 카드 리스트는 사이트 아바타·제목·아이디를 한눈에 보여 개인용 매니저에 적합.
- 흰 배경 문제는 클래식 컨트롤을 카드/WPF-UI 컨트롤로 교체하며 근본 해결된다.

### 영향
- `ShellViewModel`에 잠금/열림 두 레이아웃 모드 도입. 설정/정보 화면 신설.
- 상단 툴바의 보조 동작(OTP·마스터변경·백업/복원·시간 설정)을 설정 화면으로 이전.

### 구현 반영
검토 당시 후보였던 `ui:NavigationView`는 **채택하지 않았다**. 테마·선택 강조를 직접 통제하려고
`Border` + `SidebarNavButtonStyle`을 입힌 `ui:Button` 스택의 **커스텀 레일**로 구현했다
(`ShellWindow.xaml`, `Themes/Tokens.xaml`). 레일 항목은 계정 · 설정 · 메뉴얼 · 정보 4개이고,
잠금은 레일이 아닌 타이틀바 최좌측에 둔다. 상세는 `design-ux.md` 3절.

## TD-022. KDF 자동 상향(M5) 방식: 항목별 최댓값 + 주입 가능한 기준

- **결정일**: 2026-07-30
- **결정**: ✅ **로그인 시 저장 파라미터를 기준(floor) 이상으로 상향 — 항목별 max로만 올려 강한 항목은 낮추지 않음. 기준은 주입 가능(기본 `Recommended`)**
- **상태**: 확정

> 쉬운 말: 볼트를 열 때 저장된 열쇠계산 강도가 지금 권장치보다 약하면 **자동으로 더 강하게 다시 계산해 저장**한다.
> 단, 이미 어떤 항목이 권장치보다 세면 그건 그대로 두고 **약한 항목만 끌어올린다**(절대 약화시키지 않음).

### 배경
design 7.5·TD-015가 "로그인 시 저장 파라미터가 권장치보다 낮으면 자동 상향 후 재저장"을 이미 규정.
구현하며 두 가지 세부를 정해야 했다: (1) 상향 시 **전체를 권장치로 교체**할지 vs **항목별 max**로 올릴지,
(2) 기준치를 하드코딩할지 주입 가능하게 할지.

### 선택지 비교

| 쟁점 | 채택 | 대안 | 근거 |
|---|---|---|---|
| 상향 계산 | **항목별 max** | 전체를 권장치로 교체 | 교체는 사용자가 이미 높인 항목(예: 메모리 128MiB)을 권장치로 **낮출 위험** → max가 안전(단조 증가) |
| 기준치 | **주입 가능(기본 Recommended)** | `Recommended` 하드코딩 | 테스트가 64MiB Argon2를 반복하지 않도록 가벼운 floor 주입 가능. 운영은 기본값 그대로 |

### 구현
- `KdfParams.RaisedTo(floor)`: 항목별 `Math.Max`. `NeedsUpgradeTo(floor)`: 상향 결과가 자기 자신과 다르면 true.
- `VaultService.UpgradeKdf(vault, master, dek, newKdf)`: 새 salt·새 파라미터로 재파생해 DEK 재래핑, 본문·복구 래핑 유지(마스터·복구 두 경로 계속 유효).
- `VaultManager(store, path, kdfFloor = null)`: `Open` 시 `NeedsUpgradeTo`면 자동 상향·재저장.

### 후속 조치
- M5 나머지: 클립보드 자동 삭제, 자동 잠금, 메모리 소거.

## TD-021. 비밀번호 이력(M4): 적재 책임 위치와 상한

- **결정일**: 2026-07-30
- **결정**: ✅ **`VaultManager.Update`가 이력 권한 보유(변경 감지·적재·`LastChangedAt` 갱신), 상한 5개(초과 시 오래된 것부터 제거)**
- **상태**: 확정

> 쉬운 말: 비밀번호를 바꾸면 **이전 비번을 자동으로 이력에 쌓아** 나중에 되찾을 수 있게 한다.
> 이력 쌓는 일은 저장을 담당하는 `VaultManager` 한 곳에서만 하고, 항목당 최근 5개까지만 남긴다.

### 배경
모델에는 `PasswordHistory`·`LastChangedAt` 필드가 있으나 실제 적재 로직이 없었다(M4 미구현).
또한 `EntryEditViewModel`이 볼트 리스트의 **원본 객체를 직접 수정한 뒤** `Update`를 호출해,
`Update` 시점엔 이미 새 비번으로 덮여 있어 "이전 비번"을 알 수 없는 구조였다.

### 선택지 비교

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. Update가 이력 권한 보유 *(채택)* | `Update`가 저장된 기존 항목과 비교해 비번 변경 감지·이력 적재. VM은 원본 대신 새 `VaultEntry`를 넘김 | 이력 로직 한 곳 집중 → 단위 테스트 용이(설계 12장). "저장 전 원본 불변"도 견고해짐. VM·테스트 일부 수정 |
| B. 호출자가 이력 책임 | `Update`는 그대로, 각 호출부가 이력을 직접 쌓아 넘김 | Update 단순하나 이력 로직이 흩어지고 재사용·테스트 나쁨 |

### 확정 정책
- **적재 조건**: `Update`에서 **비밀번호가 실제로 바뀐 경우에만** 이전 비번을 이력에 적재.
- **적재 항목**: `{ Password = 기존 비번, ChangedAt = 기존 LastChangedAt }`을 최신이 앞에 오도록 삽입.
- **상한**: **5개**. 초과 시 **가장 오래된 것부터** 제거.
- **`LastChangedAt`**: 비번이 바뀐 경우에만 `now`로 갱신, 아니면 보존.
- **권한 필드**: `CreatedAt`·`PasswordHistory`는 `Update`가 기존 항목 값을 기준으로 관리(입력값 무시).
- **VM 변경**: `EntryEditViewModel`은 `_original`을 직접 수정하지 않고, 폼 값 + 보존 필드(`Id`·`Tags`·`TotpSecret`)를 담은 **새 `VaultEntry`**를 만들어 `Update`에 넘긴다.

### 후속 조치
- `VaultManager.Update` 이력 로직 + `EntryEditViewModel` 새 객체 전달로 수정. 단위 테스트로 적재·상한·미변경·`LastChangedAt` 검증.

## TD-019. TOTP 코드 계산·검증 구현: 직접 구현 vs Otp.NET

- **결정일**: 2026-07-29
- **결정**: ✅ **.NET 내장 `HMACSHA1`으로 RFC 6238 직접 구현(의존성 0)**
- **상태**: 확정

> 쉬운 말: 폰 Authenticator가 만드는 6자리 코드는 표준(RFC 6238) 계산식이 정해져 있다.
> 외부 라이브러리를 쓰지 않고 .NET에 이미 있는 암호 함수로 그 계산식을 그대로 옮겨 담았다.

### 배경
design 10장은 후보로 `Otp.NET`을 적었으나, TOTP는 HMAC-SHA1 + 동적 절단이라는 짧고
표준화된 계산이라 직접 구현이 현실적이다. 이 앱은 TD-001에서 **의존성 최소화**를 기조로 삼는다.

### 선택지 비교

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 직접 구현 *(채택)* | 내장 `HMACSHA1` + RFC 4226 동적 절단, RFC4648 Base32 코덱 | 의존성 0, 코드 ~40줄, RFC 6238 벡터로 검증. 직접 유지보수 |
| B. Otp.NET | 검증된 외부 라이브러리 | 새 NuGet 의존성. 기능은 동일 |

### 결정 근거
- RFC 6238 Appendix B 테스트 벡터 6종으로 정확성 검증 → 표준 준수 확인.
- Google Authenticator 호환을 위해 secret은 RFC4648 Base32(복구 키의 Crockford Base32와 별개, TD-018).
- 시계 오차는 앞뒤 1스텝(±30초) 허용(design 5.4).

### 후속 조치
- `PasswordManager.Core.Security.TotpValidator`(`GenerateSecret`/`GenerateCode`/`Verify`) 추가, RFC 벡터·skew·오입력 단위 테스트.

## TD-018. 복구 키 표시 인코딩: Crockford Base32 vs Base64/Hex

- **결정일**: 2026-07-29
- **결정**: ✅ **Crockford Base32 (4자 그룹, 하이픈 구분)**
- **상태**: 확정

> 쉬운 말: 복구 키는 32바이트 난수인데, 이걸 사람이 종이에 옮겨 적고 나중에 다시 입력해야
> 한다. 그래서 헷갈리는 글자(I·L·O·U)를 뺀 알파벳으로 바꾸고 `K7F2-9QX4-…`처럼 4글자씩
> 끊어 보여준다.

### 배경
복구 키는 화면에 1회 표시 후 사용자가 오프라인 보관하고(design 5.7), 분실 복구 때 **다시 입력**해
DEK를 언래핑한다(TD-010). 따라서 사람이 옮겨 적기 쉽고 오타에 관대한 왕복 가능한 인코딩이 필요하다.

### 선택지 비교

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. Crockford Base32 *(채택)* | `0-9A-Z`에서 I·L·O·U 제외, O→0·I/L→1 별칭·대소문자 무시 | 손글씨 오타에 강함, design 예시(`K7F2-9QX4`)와 일치. 표준 라이브러리 미제공(직접 구현) |
| B. Base64 | .NET 기본 제공 | 대소문자 구분·`+/=` 포함 → 손입력·구두 전달에 취약 |
| C. Hex | 단순 | 길이 2배(64자), 0/O·1/l 혼동 여지 |

### 결정 근거

- 32바이트 → 52자 → 4자 13그룹. 디코딩은 구분자·대소문자·별칭을 흡수해 재입력 실패를 줄인다.

### 후속 조치

## TD-017. CRUD 저장 시 본문 재암호화: 세션 DEK 보유 vs 저장마다 KDF 재실행

- **결정일**: 2026-07-29
- **결정**: ✅ **세션 DEK 보유 — 언락 시 1회 KDF, 저장은 DEK로 본문만 재암호화**
- **상태**: 확정

> 쉬운 말: 볼트를 열 때 딱 한 번 마스터 비번으로 (느린) 열쇠 계산을 하고, 그 결과 나온
> 데이터 열쇠(DEK)를 잠금 해제 동안만 손에 쥐고 있다가, 저장할 때는 그 열쇠로 내용만
> 새로 잠근다. 저장할 때마다 느린 열쇠 계산을 다시 하지 않는다.

### 배경
Argon2id는 의도적으로 느리다(TD-015). CRUD는 추가·편집·삭제마다 저장이 일어나므로, 저장 때마다
KDF를 다시 돌리면 매번 수백 ms 지연 + 마스터 비번 재입력이 필요해 UX가 나빠진다.

### 선택지 비교

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 세션 DEK 보유 *(채택)* | 언락 시 KDF 1회 → DEK를 세션 메모리에 보유, 저장은 DEK로 본문만 재암호화 | 빠름·비번 1회. DEK가 세션 동안 메모리에 상주(위생 강화는 M5) |
| B. 저장마다 KDF 재실행 | DEK 미보유, 저장 시 마스터 비번으로 KDF 후 재암호화 | 민감값 상주 최소화. 저장마다 수백 ms + 비번 재입력 → CRUD UX 나쁨 |

### 결정 근거
- 헤더(salt·KDF·마스터/복구 이중 래핑)는 그대로 두고 **본문만 새 nonce로 재암호화** → 복구 키 유효성 유지(TD-010).
- 메모리 상주 위험은 자동 잠금·메모리 소거(M5)로 별도 보강.

### 후속 조치
- `VaultService`에 `Unlock`(내용+DEK 반환)·`SealBody`(DEK로 본문 교체) 추가.
- `VaultManager`가 세션 동안 DEK·복호화된 `VaultData`를 보유하고 CRUD+저장 담당.

## TD-015. KDF 알고리즘: Argon2id vs PBKDF2

- **결정일**: 2026-07-29
- **결정**: ✅ **Argon2id (`Konscious.Security.Cryptography`) — memory-hard KDF 채택**
- **상태**: 확정

> 쉬운 말: 마스터 비밀번호를 암호화 키로 바꾸는 함수(KDF)를 **일부러 느리고 메모리를 많이 먹게** 만들어,
> 파일을 훔쳐 오프라인에서 비번을 무차별 대입하는 공격의 비용을 크게 키운다.

### 배경 — 위협 모델
이 앱의 모든 보안은 **마스터 비밀번호 하나에 종속**된다(design 5.6). 오프라인이 못 막는 잔여 위협이
**파일 탈취 후 오프라인 크래킹**(TD-012 배경)이라, KDF의 크래킹 저항이 실질 방어선이 된다.

### 선택지 비교

| 기준 | A. Argon2id *(채택)* | B. PBKDF2 (.NET 내장) |
|---|---|---|
| 크래킹 저항 | **memory-hard** → GPU/전용칩 병렬 공격 무력화 | CPU-hard만 → GPU 병렬에 상대적 취약 |
| 의존성 | NuGet 1개(순수 C# 구현) | **0(내장)** — TD-001 "의존성 최소화" 부합 |
| 표준/검증 | 암호 해싱 대회(PHC) 우승, 현대 권장 | FIPS 승인, 장기 검증 |

### 결정 근거
- 잔여 핵심 위협이 **오프라인 크래킹**이라, memory-hardness의 이득이 크다.
- 의존성 1개 추가는 TD-001 기조와 다소 상충하나, **가장 보안 임계적인 요소**라 예외를 둘 가치가 있다.
- design 5.2도 애초 Argon2id를 1순위로 명시 → 이를 확정.

### 파라미터 (초기 권장치, 헤더에 저장 — design 5.3)
- **메모리** 64 MiB(65536 KiB), **반복(time cost)** 3, **병렬성** 4, **출력** 32B, **salt** 16B.
- 로그인 시 저장된 파라미터가 권장치보다 낮으면 **자동 상향** 후 재저장(design 7.5).
- 값은 하드웨어·체감 속도에 맞춰 이후 조정 가능(파라미터는 헤더에 함께 저장돼 마이그레이션 불필요).

### 후속 조치
- `design.md` 5.2(KDF 확정)·10(의존성)에 반영. `PasswordManager.Core`에 Konscious 패키지 추가.

## TD-014. 슬랙 메시지 폼: 고정 문구 vs 변수 템플릿 vs 자유 텍스트

- **결정일**: 2026-07-29
- **결정**: ✅ **변수 템플릿 편집 — 화이트리스트 변수만 끼워 넣기, secret 변수는 미제공**
- **상태**: 확정

> 쉬운 말: 알림 문구를 바꾸고 싶어도, **바꿀 수 있는 재료(변수)를 안전한 것만** 준다.
> 비밀번호·아이디 같은 건 아예 변수로 제공하지 않으니 실수로도 넣을 수 없다.

### 배경
슬랙 알림 문구를 사용자가 취향에 맞게 바꾸고 싶다는 요구. 단 TD-012의 핵심 원칙
**"secret은 절대 내보내지 않는다"**를 지켜야 한다. 편집을 허용하되 유출 경로를 원천 차단해야 함.

### 선택지 비교

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 고정 문구 | 편집 불가, 앱이 정한 문구만 전송 | 가장 안전·단순하나 커스터마이즈 불가 |
| B. 변수 템플릿 *(채택)* | 허용된 변수(`{이벤트}`/`{시각}`/`{기기명}`)만 끼워 편집 | 커스터마이즈 가능 + secret 변수 미제공으로 **구조적 차단** |
| C. 자유 텍스트 | 문구를 자유롭게 작성 | 유연하나 **실수로 민감정보 삽입 위험** → TD-012와 상충 |

### 결정 근거
- 편집 자유(C)는 사용자가 실수로 비밀번호·복구 키 등을 넣을 여지를 열어 원칙과 충돌.
- 템플릿(B)은 **제공하는 변수 목록 자체에 secret이 없으므로**, 무엇을 넣어도 secret이 나갈 수 없다.
- 허용 변수: `{이벤트}`(이벤트 종류), `{시각}`, `{기기명}`. 사이트명 변수는 기본 미제공(TD-012의 사이트명 기본 미포함과 일관, 원하면 별도 토글로만).

### 정책 (확정)
- **편집 대상**: 알림 문구 템플릿 문자열. 예: `🔓 {이벤트} · {시각}`.
- **허용 변수만 치환**: 화이트리스트 외 토큰(`{…}`)은 그대로 리터럴 출력(치환 안 함) → 우회 불가.
- **미리보기 제공**: 저장 전 실제 전송될 문구를 예시로 보여줌.
- **기본 템플릿 복원** 버튼 제공.

### 후속 조치
- `design.md` 7.8(전송 내용)·7.9(설정 모듈)·`ui.md` S7·`flows.md` 7에 반영.

## TD-013. 네트워크 전역 스위치: 전역 오프라인 킬스위치 vs 기능별 토글만

- **결정일**: 2026-07-29
- **결정**: ✅ **전역 오프라인 스위치 도입 — 모든 아웃바운드를 막는 상위 차단기, 기본 ON(차단)**
- **상태**: 확정

> 쉬운 말: 슬랙 토글이 "이 알림 켤까?"라면, 전역 스위치는 "이 앱이 **아예 인터넷을 쓰게 할까**?"라는

### 배경
현재 유일한 네트워크 기능은 슬랙(옵트인·기본 OFF, TD-012). 로컬 전용 원칙을 **UI에서 명시적으로
보증**하고, 앞으로 네트워크 기능이 늘어도 **한 곳에서 통제**할 상위 지점이 필요.

| C. 전역 스위치, 기본 허용 | 전역 스위치를 두되 기본 OFF(허용) | 통제점은 생기나 기본값이 로컬 원칙과 덜 맞음 |

### 결정 근거

- 슬랙을 처음 켜려면 **전역 오프라인 해제 → 슬랙 ON** 2단을 거친다(의도된 이중 확인).
- 전역 스위치 자체는 설정 모듈의 **네트워크 섹션**에 배치(7.9).

### 후속 조치
- `design.md` 1(원칙)·7.8·7.9(설정 모듈)·`ui.md` S7·`flows.md` 7에 반영.

사이트별 저장 필드를 **사이트명·URL·아이디·비밀번호·메모·태그**로 단순화하기로 함.
이때 기존 고정 분류(`category`: GAME/SITE/OTHER)와 새 "계정 인식 태그"가 역할이 겹침.

### 선택지 비교

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 자유 태그 *(채택)* | category 제거, 자유 태그로 분류·구분·필터 | 유연(원하는 분류 자유), 여러 계정 구분도 한 번에. UI 단순 |
| B. 카테고리 + 태그 | 큰 분류는 category, 세부는 태그 | 기능은 풍부하나 입력·필터 UI가 복잡 |

### 결정 근거
- 태그 하나로 **분류 + 같은 사이트 여러 계정 구분(TD-003)**을 동시에 해결 → 단순·유연.
- `loginType`(USERNAME/EMAIL)도 제거: **아이디 한 칸이 문자·이메일 겸용**(형식 자동 구분 불필요).

### 후속 조치
- `design.md` 6(데이터 모델: `category`/`loginType` 제거, `tags[]` 추가)·7.3(태그 필터)·8(사이드바 태그) 반영 완료.

## TD-010. 마스터 비밀번호 복구: 복구 키 vs OTP/이메일/폰 vs 복구 없음

- **결정일**: 2026-07-29
- **결정**: ✅ **복구 키(Recovery Key) — 최초 설정 시 무조건 발급 + "안전 보관 확인" 체크**
- **상태**: 확정

> 쉬운 말: 마스터 비밀번호는 이 앱의 유일한 열쇠라, 잊으면 원칙적으로 금고를 못 연다.
> 그래서 최초 설정 때 **비상용 열쇠(복구 키)**를 만들어 **종이 등 오프라인에 보관**하게 하고,
> 나중에 비번을 잊으면 그 복구 키로 금고를 열어 새 비번을 정한다.

### 배경 — 왜 어려운 문제인가
데이터는 마스터 비번으로 만든 열쇠로 잠겨 있어, 진짜로 잊으면 **수학적으로 복호화 불가**다.
"복구 가능"하게 하려면 **열쇠로 가는 또 다른 길**을 미리 만들어야 하고, 그 길도 안전하게 지켜야 한다.

### 선택지 비교

| 선택지 | 방식 | 트레이드오프 |
|---|---|---|
| A. 복구 키 *(채택)* | DEK를 마스터키뿐 아니라 **복구 키로도 감싸** 저장, 오프라인 보관 | 로컬·무백도어 유지. 사용자가 복구 키를 안전 보관해야 함(둘 다 잃으면 소실) |
| B. OTP/폰 | 6자리 OTP로 복구 | ❌ OTP secret이 금고 안에 있어 **닭-달걀**. OTP는 열쇠가 아니라 게이트(TD-004). 폰 분실에 취약 |
| C. 이메일 | 서버가 재설정 토큰 발송 | ❌ **로컬 전용 원칙 위반**(네트워크·서버 필요), 사실상 백도어 |
| D. 보안 질문 | 질문 답으로 복구 | ❌ 답이 추측되기 쉬워 **약한 비번**이나 마찬가지 |
| E. 복구 없음 | 잊으면 데이터 포기 | 가장 단순·안전하나, 잊으면 전부 소실 |

### 결정 근거
- **OTP·이메일·폰은 구조적으로 부적합**: OTP는 금고 안에 갇혀 있고(B), 이메일은 로컬 원칙을 깬다(C).
- 복구 키(A)는 이미 채택한 **2단 키 구조에 자연스럽게 결합**(DEK를 열쇠 하나 더로 감싸기만 하면 됨).
- 서버·이메일 없이 **완전히 로컬**로 복구가 성립. 1Password의 Secret Key 복구와 같은 접근.

### 발급 정책 (확정)
- **무조건 발급**: 최초 설정 때 복구 키를 반드시 만든다(건너뛰기 불가).
- **보관 확인 체크**: "안전한 곳에 보관했다" 체크를 받아야 설정 완료.
- 복구 키는 **평문으로 앱·PC에 저장하지 않는다**(저장하면 백도어가 됨).

### 후속 조치
- `design.md` 5.2·5.3(이중 래핑)·5.7(복구 흐름)·7.6·8(UX)·13(한계)에 반영 완료.

### 한계 (고지 필수)
- **마스터 비번 + 복구 키를 둘 다 잃으면 복구 불가.** (백도어를 두지 않는 대가)

## TD-009. 마스터 비밀번호 강도 정책 (잠정 — 재검토 예정)

- **결정일**: 2026-07-29
- **결정**: ✅ **길이 중심 단순 규칙(외부 라이브러리 없음) — 마스터 비밀번호에만 적용, 최소 12자 + 흔한 비번 차단**
- **상태**: 확정

> 쉬운 말: 금고 문(암호화)이 아무리 튼튼해도, 그 열쇠인 **마스터 비밀번호를 약하게 만들면 전부 헛수고**다.
> 그래서 마스터 비번은 설정할 때 **충분히 길게** 만들도록 강제한다. (사이트별 비번은 제한 없이 자유)

### 배경
이 앱의 모든 보안이 **마스터 비밀번호 하나에 종속**된다(볼트 복호화·OTP 재설정이 모두 여기 매달림).
따라서 설정 단계에서 강도를 강제할 필요가 있다.

### 강도 측정 방식 비교

| 방식 | 내용 | 트레이드오프 |
|---|---|---|
| 추측 난이도(zxcvbn) | "얼마나 쉽게 추측되나"를 0~4점으로 채점 | 정확하지만 **외부 의존성 + 사전 데이터**가 붙음(TD-001 "의존성 최소화"와 상충) |
| **길이 중심 규칙** *(채택)* | 최소 길이 강제 + 아주 흔한 비번 소량 차단 | 의존성 0. 정밀도는 약간 낮지만 **길이가 곧 강도**라 실용상 충분(NIST도 길이 우선) |

### 확정 정책
- **적용 대상: 마스터 비밀번호만.** 사이트별 비번은 사이트마다 요구가 달라 **길이 제한 없이 유동적**(생성기로 자유 선택).
- **측정**: 길이 중심 단순 규칙 — 외부 라이브러리 없이 구현.
- **하한(강제)**: **최소 12자** → 미달 시 거부.
- **흔한 비번 차단**: `password`, `123456` 등 소량 내장 차단목록에 걸리면 거부.
- **상한**: 넉넉히(예: 128자) — 외우기 쉬운 **패스프레이즈** 허용.
- 설정 화면에 **길이 기반 강도 막대**(참고용) 표시, 생성기의 패스프레이즈 모드 유도.
- **비밀번호 힌트 기능은 두지 않음** — 힌트가 곧 공격 단서가 되고, 복구불가 원칙과 상충.

### 결정 근거
- 이 앱은 **의존성 최소화**를 중시(TD-001). 마스터 비번 하나 검사하려고 zxcvbn+사전을 끌어오는 건 과함.
- 마스터 비번은 어차피 **생성기(패스프레이즈)로 강하게 유도**하므로, 하한(길이)만 막아도 실효 충분.

### 후속 조치
- `design.md` 5.6에 반영 완료(잠정 → 확정).

## TD-008. 저장 형식 변화 대응: 명시적 마이그레이션 vs 관대한 파싱

- **결정일**: 2026-07-29
- **결정**: ✅ **둘 다 — 구조 변경은 버전별 변환, 단순 필드 추가는 기본값으로 흡수**
- **상태**: 확정

> 쉬운 말: 앱을 새로 내면 저장 파일의 모양이 바뀔 수 있다. 그때 **옛날 파일도 열 수 있게** 하는 규칙.

### 선택지 비교

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 명시적 마이그레이션 | 파일의 `version`을 보고 v1→v2→… 순서로 변환 | 구조가 바뀌어도 안전. 변환 코드가 조금 늘어남 |
| B. 관대한 파싱 | 없는 필드는 기본값으로 채워 읽음 | 필드 추가엔 편하나, 구조가 바뀌면 대응 불가 |
| A+B *(채택)* | 필드 추가는 B로, 구조 변경은 A로 | 두 방식의 장점만. 규칙만 지키면 됨 |

### 결정 근거
- `version` 필드는 이미 있음 → 올릴 때 변환 함수만 연결.
- 대부분의 변화는 "필드 하나 추가" 수준 → 관대한 역직렬화로 무비용 처리.

### 후속 조치
- `design.md` 5.3(파일 포맷)·6(데이터 모델)에 버전 규칙 명시.

## TD-006. 키 구조: 마스터키로 직접 암호화 vs 2단 키(마스터키→데이터키)

- **결정일**: 2026-07-29
- **결정**: ✅ **2단 키 구조 — 데이터는 랜덤 데이터키로 암호화하고, 그 데이터키를 마스터키로 감싸 저장**
- **상태**: 확정

> 쉬운 말: 금고 안에 **작은 열쇠(데이터키)**를 하나 넣어 실제 자물쇠를 잠근다. 마스터 비번은 그 **작은 열쇠를 넣어둔 서랍을 여는 데만** 쓴다. 그래서 마스터 비번을 바꿔도 서랍 자물쇠만 바꾸면 되고, 안의 내용물은 그대로 둔다.
>
> (용어) 감싸는 바깥 열쇠 = KEK, 실제 데이터를 잠그는 안쪽 열쇠 = DEK.

### 배경
TD-002·1번 논의에서 나온 두 필요를 한 번에 푼다: **마스터 비번 변경(rekey)**과 **KDF 파라미터 강화**. 마스터키로 데이터를 직접 암호화하면 둘 다 매번 **전체 재암호화**가 필요하다.

### 선택지 비교

| 선택지 | 비번 변경 시 | KDF 강화 시 | 복잡도 |
|---|---|---|---|
| A. 마스터키로 직접 암호화 | 전체 재암호화 | 전체 재암호화 | 단순 |
| B. 2단 키 *(채택)* | **데이터키 재포장만** | **데이터키 재포장만** | 약간 증가 |

### 결정 근거
- 마스터 비번 변경·KDF 강화가 **데이터키만 다시 감싸는** 값싼 작업이 됨(데이터 그대로).
- 1Password 등 실무 비밀번호 관리자의 표준 구조.
- 데이터 규모가 작아 A의 재암호화 비용이 크진 않지만, **비번 변경/보안 강화 흐름이 깔끔**해지는 이점이 큼.

### 후속 조치
- `design.md` 5.2(암호화 파이프라인)·5.3(파일 포맷: 감싼 데이터키 저장)에 2단 키 반영.
- 마스터 비번 변경 기능(7장)과 로그인 시 KDF 자동 강화 추가.
- ⚠️ 용어 주의: TD-001의 "봉투 암호화(파일 통짜 암호화)"와 구분 — 여기서는 **키를 감싸는(wrap)** 2단 구조를 뜻함.

## TD-005. OTP·폰 분실 복구: 복구 코드 vs 마스터 비번으로 재설정

- **결정일**: 2026-07-29
- **결정**: ✅ **마스터 비번으로 OTP 재설정(새 secret·QR 재발급)**
- **상태**: 확정

> 쉬운 말: 폰을 잃어 6자리 코드를 못 넣으면 비밀번호를 못 보게 된다. 그때 **마스터 비번만 다시 넣으면 폰 등록을 새로** 할 수 있게 한다.

### 선택지 비교

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 복구 코드 | 등록 시 일회용 백업 코드 발급, 오프라인 보관 | OTP가 금고 열쇠일 때 유용. 사용자가 코드를 따로 보관해야 함 |
| B. 마스터 비번으로 재설정 *(채택)* | 설정에서 마스터 비번 재입력 → 새 secret·QR | 단순·자연스러움. OTP가 마스터 비번에 종속됨 |

### 결정 근거
- TD-004에서 OTP를 **"열람 재확인 게이트"**로 규정 → OTP는 금고 열쇠가 아님.
- 그러므로 마스터 비번으로 재설정(B)이면 충분하고, 복구 코드는 과함.
- **명시할 점**: 마스터 비번을 알면 OTP를 우회 재설정할 수 있음(= OTP는 마스터 비번에 종속). 이는 TD-004의 "게이트" 규정과 일관.

## TD-004. 개별 열람 OTP의 역할: 암호학적 2차 잠금 vs 열람 재확인 게이트

- **결정일**: 2026-07-29
- **결정**: ✅ **OTP는 "열람 재확인 게이트"로 규정 + 비밀번호는 지연 복호화**
- **상태**: 확정

> 쉬운 말: 금고를 한 번 열면(마스터 비번 입력) 안의 비밀번호가 **다 읽히는 상태**가 된다. 그러면 개별 "보기"에서 6자리 OTP는 화면에 **보여줄지 말지**만 막는 셈이라 진짜 잠금은 아니다. 그래서 (1) OTP의 역할을 솔직히 "재확인용 문지기"로 정하고, (2) 각 비밀번호는 **평소엔 잠가 두고 "보기" 누른 순간에만 푼다**.

### 배경
당초 R5는 OTP를 "진짜 2단계 인증"으로 표현했으나, 마스터 비번으로 금고를 열면 모든 평문이 이미 메모리에 올라오는 구조라 개별 OTP는 암호학적 방벽이 아니다. 또한 TOTP(6자리)는 **엔트로피(무작위성의 양)가 작아** 암호 열쇠 재료로 부적합.

### 선택지 비교

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. OTP를 암호 키 재료로 | 항목 복호화에 OTP를 섞음 | 6자리라 보안 이득 미미, 30초마다 값이 바뀌어 키로 부적합. 비표준 |
| B. 게이트로 규정 *(채택 일부)* | OTP는 열람 시 재확인 문지기로 목표를 정직하게 명시 | 구현 단순. 어깨너머·자리비움 방어 수준 |
| C. 지연 복호화 *(채택 일부)* | 비번 필드는 항목별로 따로 암호화, 열람 순간에만 복호화 | 평소 메모리에 평문 비번이 없어 노출 시간 최소화 |

### 결정 근거
- OTP를 키 재료로 쓰는 A는 보안 이득이 거의 없고 표준에서 벗어남 → 배제.
- 대신 **B로 목표를 정직하게 규정**하고, **C로 실제 노출을 줄인다**(항목별 개별 암호화 + 지연 복호화).

### 후속 조치
- `design.md` 5.1·5.4(OTP 목표 문구)·6(항목별 password 개별 암호화)·7.4에 반영.
- R5 문구를 "열람 재확인(2단계 게이트)"으로 조정.

## TD-003. 한 사이트 여러 계정: 평면(flat) vs 계층(site→accounts)

- **결정일**: 2026-07-29
- **결정**: ✅ **평면(A) — 각 계정을 독립 `entry`로 저장, 목록에서 사이트명 기준 그룹핑 표시**
- **상태**: 확정

### 선택지 비교

| 선택지 | 구조 | 트레이드오프 |
|---|---|---|
| A. 평면 *(채택)* | 같은 사이트명/URL의 `entry`를 여러 개 허용 | 모델 변경 최소(기존 `entries[]` 그대로). Bitwarden 등 대다수 방식. 유연 |

### 후속 조치
- `docs/design.md` R1·데이터 모델·UX(목록 그룹핑)에 반영 완료.

## TD-002. 비밀번호 만료 관리: 만료 알림 vs 이력만 보관

- **결정일**: 2026-07-29
- **결정**: ✅ **만료 주기·알림 제거, 마지막 변경일 + 변경 이력만 보관**
- **상태**: 확정

### 배경
"주기적으로 바꿔야 하는데 이전 비밀번호를 잊는다"는 원래 고민에 대응하는 방법으로,
만료 주기(`rotationDays`) + 자동 알림을 둘지 검토.

### 선택지 비교

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| A. 만료 주기 + 자동 알림 | 항목별 주기 설정, 만료 임박 배지·알림 | 사이트마다 주기가 달라 관리 번거로움. 알림 뜰 때마다 변경 강요되는 느낌 |
| B. 이력만 보관 *(채택)* | 만료 주기·알림 없음. `lastChangedAt`·`passwordHistory`만 유지 | 능동 알림 없음. 대신 접속 시 사용자가 직접 확인·판단 |

### 결정 근거
- 사이트마다 **변경 주기가 제각각**이라 일괄 만료 정책이 실효성이 낮음.
- 항목이 많아지면 **알림에 맞춰 매번 변경하는 것 자체가 부담**.
- 원래 핵심 니즈(이전 비밀번호 분실 방지)는 **변경 이력**으로 충족되고,
  "언제 바꿨는지"는 **마지막 변경일**로 접속 시 직접 확인하면 충분.

### 채택에 따른 후속 조치
- 데이터 모델에서 `rotationDays`, 만료일 계산(`nextChangeDue`) 제거.
- `lastChangedAt`, `passwordHistory` 유지 → 상세 화면에 표시.
- `docs/design.md`의 R3·데이터모델·기능(7장)·UX·로드맵(M4)에 반영 완료.

## TD-001. 저장 방식: 파일 봉투 암호화 vs 무설치 DB

- **결정일**: 2026-07-29
- **결정**: ✅ **파일 봉투 암호화** (단일 암호화 파일 `vault.dat`에 볼트 전체를 통째로 암호화)
- **상태**: 확정

### 배경
로컬 전용·무설치가 전제. 저장을 "파일 통짜 암호화"로 할지, "무설치 임베디드 DB"로 할지 결정 필요.

### 선택지 비교

| 기준 | A. 파일 봉투 암호화 *(채택)* | B. SQLite + SQLCipher | C. LiteDB |
|---|---|---|---|
| 실무 검증도 | 직접 구현(로직 단순) | ⭐ 매우 높음 (업계 표준) | 낮음~보통 |
| 암호화 | 전체 통짜 암호화 → **추론 명확** | SQLCipher 네이티브 번들 필요 | AES 내장 |
| 쓰기 중 크래시 안전성 | 직접 대응 필요(원자적 쓰기) | ⭐ ACID 트랜잭션 | 트랜잭션 있음(검증 약함) |
| 부분 업데이트/쿼리 성능 | 매번 전체 재암호화(데이터 작아 체감 0) | ⭐ 우수 | 우수 |
| 구현 복잡도/의존성 | ⭐ 최소, 완전 통제 | 네이티브 바이너리 번들 | NuGet 하나 |
| 이 앱 적합도 | ⭐ 규모에 최적 | 과함 | 편하나 검증 약함 |

### 결정 근거
- **데이터 규모가 작다**: 비밀번호는 많아야 수십~수백 건 → DB의 성능·쿼리 이점이 사실상 놀게 됨.
- **보안 추론의 단순함이 최우선**: "파일은 항상 완전 암호문, 앱이 켜진 동안만 메모리에 평문"이라는 모델이 감사·검증하기 쉬움. 신뢰해야 할 대상(DB 엔진의 암호화 구현)이 늘지 않음.
- **의존성 최소화**: 네이티브 번들(SQLCipher)이나 검증도 낮은 라이브러리(LiteDB)를 끌어들이지 않음.
- LiteDB는 편의성은 좋으나 SQLite만큼 실무 검증되지 않아, "DB를 쓸 바엔 SQLite"라는 결론 → 그런데 이 규모엔 DB 자체가 불필요.

### 채택에 따른 후속 조치 (약점 보완)
- 파일 방식의 유일한 약점인 **"쓰기 중 크래시 → 파일 손상"** 은 아래로 대응:
  - **원자적 쓰기**: 임시 파일에 먼저 쓰고, 성공 시 기존 파일과 교체(rename).
  - **자동 백업**: 저장 전 `vault.dat.bak`로 이전 파일 보존.
- 위 내용을 `docs/design.md`(5.3 볼트 파일 포맷) 저장 로직에 반영한다.

### 재검토 트리거 (아래 상황이면 DB 재고)
- 항목이 수천 건 이상으로 증가.
- 복잡한 다중 조건 쿼리·통계 요구 증가.
- 트랜잭션·무결성을 직접 구현하는 부담이 커질 때 → 이 경우 SQLite 우선 검토.
