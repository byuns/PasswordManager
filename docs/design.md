# PasswordManager 설계 문서

> 로컬 전용 데스크톱 비밀번호 관리자 (Windows / .NET / WPF)

---

## 1. 개요 & 목표

여러 사이트·게임마다 서로 다른 아이디(또는 이메일)와 비밀번호를 안전하게 보관하고,
주기적으로 변경해야 하는 계정의 이전 비밀번호까지 잃어버리지 않도록 관리하는
**내 PC에서만 동작하는 데스크톱 앱**.

핵심 원칙:

- **로컬 전용**: 클라우드 동기화 없음. 모든 데이터는 이 PC에만 존재.
  - **유일한 예외**: **슬랙 알림**(옵트인, 기본 OFF). 무단 접근·변경을 원격으로 탐지하기 위한
    **아웃바운드 알림만** 허용하며, 비밀번호 등 민감정보는 절대 전송하지 않는다(TD-012, 7.8).
  - **전역 오프라인 스위치(TD-013)**: 모든 아웃바운드를 막는 상위 차단기를 두고 **기본 ON(차단)**.
    슬랙 등 네트워크 기능은 그 하위에 종속되며, 전역 스위치를 해제해야만 개방된다(7.9).
- **무설치 저장**: 별도 DB 엔진 설치 없이 **단일 암호화 파일**에 저장.
- **강한 암호화**: 마스터 비밀번호로 파생한 키로 볼트 전체를 암호화.
- **2단계 열람 보호**: 개별 비밀번호를 볼 때 **OTP(2FA)** 를 추가로 요구.

---

## 2. 핵심 요구사항

| # | 요구사항 |
|---|---|
| R1 | 사이트/게임별로 **아이디 또는 이메일 + 비밀번호** 저장 (**한 사이트에 여러 계정** 등록 가능) |
| R2 | 데이터를 **파일 기반으로 암호화** 저장 (DB 미사용) |
| R3 | 비밀번호 변경 시 **이전 비밀번호 이력 + 마지막 변경일** 보관 (분실 방지, 변경 시점 확인) |
| R4 | 앱을 켜면 **사이트 + 아이디/이메일 목록**이 보이고, 비밀번호는 가려짐 |
| R5 | 비밀번호 열람 시 **OTP 재확인 게이트**(폰 Google Authenticator)를 통과해야 함 (TD-004) |
| R6 | 검색/필터로 원하는 계정을 빠르게 찾기 |

> **만료 알림 제외 (2026-07-29 결정, tradeoffs TD-002)**: 사이트마다 변경 주기가 다르고
> 알림에 맞춰 매번 바꾸는 것도 번거로워, 만료 주기·알림 기능은 넣지 않는다. 대신
> **마지막 변경일과 변경 이력**만 보관해, 사용자가 해당 사이트 접속 시 직접 확인·판단한다.

## 4. 아키텍처

계층을 명확히 분리해 **민감 로직(암호화·OTP)** 과 **UI** 를 격리한다.

```
┌─────────────────────────────────────────────┐
│  Presentation (WPF / XAML)                    │  ← 화면, 버튼, 목록
│  - Views, ViewModels (MVVM)                   │
├─────────────────────────────────────────────┤
│  Application (Services)                        │  ← 유스케이스 조합
│  - VaultService, AuthService, OtpService      │
│  - PasswordHistoryService (비밀번호 이력)       │
├─────────────────────────────────────────────┤
│  Core / Security                              │  ← 순수 로직 (테스트 용이)
│  - KeyDerivation (Argon2id)                   │
│  - VaultCrypto (AES-256-GCM)                  │
│  - TotpValidator                              │
├─────────────────────────────────────────────┤
│  Storage                                      │  ← 파일 I/O
│  - VaultFileStore (vault.dat 읽기/쓰기)        │
└─────────────────────────────────────────────┘
```

**핵심 규칙**: 복호화된 평문 비밀번호·마스터 키는 Core/Application 계층에만 머물고,
UI에는 필요한 순간에만 전달하며 사용 후 즉시 폐기한다.

## 5. 보안 설계

### 5.1 인증 2계층

| 계층 | 시점 | 수단 | 역할 |
|---|---|---|---|
| **1차: 마스터 비밀번호** | 앱 시작 시 1회 | 사용자가 아는 비밀번호 | 볼트 파일 복호화 (없으면 목록조차 못 봄) |
| **2차: OTP (TOTP)** | 개별 비밀번호 열람 시 | 폰 Google Authenticator의 6자리 | **열람 재확인 게이트** (TD-004) |

> **참고 — 마스터 비밀번호는 왜 필수인가?**
> 파일 기반 암호화는 "키"가 있어야 성립합니다. 그 키를 안전하게 만드는 유일한 출발점이
> 사용자의 마스터 비밀번호입니다. 따라서 "앱을 켜면 목록이 보인다"는 흐름은
> **정확히는 "마스터 비밀번호 1회 입력 → 볼트 복호화 → 목록 표시"** 가 됩니다.
> (이후 개별 비밀번호를 볼 때만 OTP를 추가로 요구)

> **참고 — 2차 OTP의 역할 (TD-004)**: 마스터 비번으로 볼트를 열면 내부 값은 이미 앱이 다룰 수 있는
> 상태가 됩니다. 그래서 개별 열람 OTP는 *암호학적 2차 잠금*이 아니라 **"열람 재확인 문지기"**로
> 목표를 규정합니다(어깨너머 훔쳐보기·자리비움 방어). 대신 각 비밀번호는 평소엔 잠가 두고
> **"보기"를 누른 순간에만 푸는 지연 복호화**(5.2·6장)로 실제 노출 시간을 최소화합니다.

### 5.2 암호화 파이프라인 — 2단 키 구조 (TD-006)

> **쉬운 말**: 금고 안에 **작은 열쇠(데이터키)**를 넣어 실제 자물쇠를 잠그고, 마스터 비번은
> 그 작은 열쇠를 **감싸 두는 데만** 씁니다. 그래서 마스터 비번을 바꿔도 작은 열쇠만 다시 감싸면
> 되고, 안의 내용물은 다시 암호화할 필요가 없습니다.
> (용어) 감싸는 바깥 열쇠 = **KEK**(Key-Encryption Key), 데이터를 잠그는 안쪽 열쇠 = **DEK**(Data-Encryption Key).

```
① 마스터 비밀번호 + salt(16B) ─[ Argon2id KDF ]→ 마스터키(KEK, 256-bit)   ← 무차별 대입 방어
② 데이터키(DEK, 랜덤 256-bit) + nonce(12B) ─[ AES-256-GCM ]→ 암호문 + 인증 태그   ← 기밀성 + 무결성
③ 데이터키(DEK)를 두 열쇠로 각각 감싸(wrap) 헤더에 저장
     - 마스터키(KEK)로 감싼 것         → 평소 열기용
     - 복구 키(Recovery Key)로 감싼 것  → 비번 분실 시 복구용 (TD-010)

   ▶ 마스터 비번 변경·KDF 강화 = ③의 마스터 쪽만 다시 감싸기 = 데이터(②) 재암호화 불필요
```

- **KDF**: **Argon2id** (라이브러리 `Konscious.Security.Cryptography`) — **확정(TD-015)**.
  - 파라미터(초기 권장치): 메모리 64 MiB, 반복 3, 병렬성 4, 출력 32B, salt 16B. 헤더에 저장·자동 상향(7.5).
  - 검토했던 대안: .NET 내장 **PBKDF2**. 의존성은 0이나 memory-hard가 아니라 오프라인 크래킹 저항이 약해 배제(TD-015).
- **대칭 암호화**: **AES-256-GCM** (.NET 내장 `System.Security.Cryptography.AesGcm`).
  - GCM은 암호화와 동시에 **인증 태그**를 생성 → 파일이 변조되면 복호화 자체가 실패.
- **2단 키(KEK/DEK)**: 데이터는 랜덤 **데이터키(DEK)**로 암호화하고, 그 DEK를 마스터키(KEK)로 감싸 헤더에 저장.
  - 마스터 비번 변경(rekey)·KDF 파라미터 강화 시 **DEK를 다시 감싸기만** 하면 됨(데이터 그대로).
- **복구 키(Recovery Key, TD-010)**: 최초 설정 때 길고 무작위한 복구 키를 발급하고, **같은 DEK를 복구 키로도 한 번 더 감싸** 저장한다.
  - 마스터 비번을 잊으면 복구 키로 DEK를 풀어 **새 마스터 비번을 다시 설정**한다(서버·이메일 불필요, 로컬 유지).
- **salt / nonce**: 암호학적 난수(`RandomNumberGenerator`)로 생성, 파일 헤더에 함께 저장.
- **nonce 재사용 금지**: 저장할 때마다 새 nonce 생성.

### 5.3 볼트 파일 포맷 (`vault.dat`)

```
┌────────────────────────────────────────────┐
│ Magic (4B)   : "PWMV"                        │
│ Version (1B) : 0x01                          │
│ KDF params   : algo, memory, iterations, ... │
│ Salt (16B)                                   │
│ WrappedDEK(master)  : KEK로 감싼 데이터키      │  ← 평소 열기 (TD-006)
│ WrappedDEK(recovery): 복구 키로 감싼 데이터키   │  ← 분실 복구 (TD-010)
│ Nonce (12B)                                  │
├────────────────────────────────────────────┤
│ Ciphertext   : AES-256-GCM( JSON(vault) )    │  ← DEK로 암호화
│ Auth Tag(16B)                                │
└────────────────────────────────────────────┘
```

- 헤더는 평문(복호화에 필요한 파라미터) / 본문(실제 데이터)은 전부 암호화.
- **감싼 데이터키(Wrapped DEK)**는 마스터용·복구용 두 벌을 헤더에 저장하되, 각 열쇠 없이는 풀 수 없으므로 안전.
- 저장 위치 후보: `%APPDATA%\PasswordManager\vault.dat`.
- **원자적 쓰기**: 새 내용을 임시 파일(`vault.dat.tmp`)에 먼저 완전히 쓰고, 성공하면
  기존 파일과 **교체(rename)** 한다. 쓰기 도중 크래시가 나도 기존 `vault.dat`은 온전히 남는다.
- **자동 백업**: 교체 직전 이전 파일을 `vault.dat.bak`로 보존(파일 손상·롤백 대비).
- **버전 마이그레이션 (TD-008)**: 로드 시 `Version`을 확인해, 구조가 바뀌었으면
  버전별 변환(v1→v2→…)을 순서대로 적용한 뒤 최신 버전으로 다시 저장한다.
  단순 필드 추가는 관대한 역직렬화(없는 필드는 기본값)로 흡수한다.
- **복호화 실패 원인 구분 (2단 키 활용)**: 금고를 못 열었을 때 원인을 나눠 안내한다.
  - 감싼 데이터키(Wrapped DEK)를 못 풀면 → 대개 **마스터 비밀번호 오류** → 다시 입력 안내.
  - DEK는 풀렸는데 본문 복호화(인증 태그 검증)가 실패하면 → **파일 손상** → `vault.dat.bak`로 복구 안내.
  - 쉬운 말: "열쇠를 못 넣은 것"과 "금고 안이 부서진 것"을 나눠서, 사용자에게 알맞은 다음 행동을 알려준다.

### 5.4 OTP(TOTP) 설계 — 열람 재확인 게이트 (TD-004)

**목적**: 비밀번호 열람 시, 마스터 비번으로 이미 열린 상태에서 **한 번 더 확인**하는 문지기 역할.
어깨너머 훔쳐보기·자리비움 상황을 막는 것이 목표이며, *암호학적 2차 잠금은 아니다*(근거·한계는 TD-004).

- **표준**: TOTP (RFC 6238), HMAC-SHA1, 30초 주기, 6자리.
- **시간 오차 허용(clock skew)**: 검증 시 앞뒤 1스텝(±30초)까지 허용해 폰·PC 시계 차이를 흡수.
- **secret 저장**: 앱 잠금해제용 OTP secret은 **볼트 안에 데이터키로 암호화**되어 저장.
  → 파일만 유출돼도 마스터 비번 없이는 secret을 꺼낼 수 없음.

**등록 흐름 (최초 1회)**:
```
앱이 secret 생성 → 화면에 QR코드 표시(QRCoder)
   → 사용자가 [폰의 Google Authenticator]로 QR 스캔
   → 폰과 앱이 같은 secret 공유 완료
```

**사용 흐름 (비밀번호 볼 때마다)**:
```
[비밀번호 보기] 클릭
   → OTP 입력창 표시
   → 폰 Google Authenticator의 6자리 확인 후 입력
   → 앱이 저장된 secret으로 TOTP 계산·검증 (Otp.NET)
   → 일치하면 해당 비밀번호를 그 순간에 복호화하여 표시 (지연 복호화)
```

**OTP 재설정 (폰 분실 대비, TD-005)**:
```
설정 → OTP 재설정
   → 마스터 비밀번호 재입력 (본인 확인)
   → 앱이 새 secret 생성 → 새 QR 표시 → 폰으로 다시 등록
```
- 즉 **마스터 비번을 알면 OTP를 새로 등록**할 수 있다(OTP는 마스터 비번에 종속).
  복구 코드는 두지 않는다 — OTP가 금고 열쇠가 아니라 게이트이기 때문(TD-004·TD-005).

> **QR 스캔 방향 주의**: 앱 잠금해제 2FA에서 카메라 스캔은 **폰이 앱 화면의 QR을 스캔**하는
> 방향입니다(앱→폰). PC 웹캠 스캔은 미채택(아래 "사이트별 OTP 보관" 참고)이라, 앱은 QR을 **표시만** 하고 읽지 않습니다.

**(선택) 사이트별 OTP 보관 기능**:
- 각 서비스가 제공하는 2FA secret을 `otpauth://` URI 붙여넣기로 저장 → 앱이 해당 사이트의 6자리 코드도 생성.
- 이 secret들도 모두 볼트 내부에 암호화 저장.
- 편의 기능이며, 앱 잠금해제 2FA와는 별개.
- ~~**PC 웹캠 QR 스캔**(ZXing.Net + OpenCvSharp)~~ — **미채택으로 결정(2026-07-31)**. 카메라 라이브러리 의존성이 TD-001 "의존성 최소화"와 상충하고, `otpauth://` 붙여넣기로 대체 가능해 범위에서 제외.

### 5.5 메모리·클립보드 위생 & 실행 제어

- 마스터 키/평문 비밀번호는 사용 후 배열을 `Array.Clear`로 즉시 소거.
- **지연 복호화**: 볼트를 열 때 개별 비밀번호는 암호문 상태로 두고, 열람하는 순간에만 복호화해
  평소 메모리에 평문 비밀번호가 떠 있는 시간을 최소화한다(6장·TD-004).
- 비밀번호 복사 시 **클립보드 자동 삭제 타이머**(예: 20초 후 비움).
- 화면의 비밀번호는 기본 마스킹(`••••`), 명시적 요청 시에만 표시.
- 일정 시간 미조작 시 **자동 잠금**(볼트 닫고 다시 마스터 비번 요구).
- **단일 인스턴스 (TD-007)**: 실행 시 Named Mutex로 이름표를 걸어, 앱이 **두 번 실행되지 않게** 막는다.
  → 두 인스턴스가 같은 볼트 파일을 동시에 저장하다 손상시키는 일을 원천 차단.

### 5.6 마스터 비밀번호 강도 — 길이 중심 규칙 (TD-009)

> **쉬운 말**: 금고 문(암호화)이 튼튼해도 그 **열쇠인 마스터 비밀번호가 약하면 전부 헛수고**다.
> 이 앱의 모든 보안(볼트 복호화·복구·OTP 재설정)이 마스터 비밀번호 하나에 매달려 있으므로,
> 설정 단계에서 **충분히 길게** 만들도록 강제한다.

- **적용 대상: 마스터 비밀번호만.** 사이트별 비밀번호는 사이트마다 요구가 달라 **길이 제한을 두지 않고 유동적**으로 둔다(생성기로 8~64자 등 자유 선택 — 7.1).
- **측정 방식: 길이 중심 단순 규칙** — 외부 라이브러리(zxcvbn 등) 의존성 없이 구현(TD-001의 "의존성 최소화" 기조 유지).
- **하한(강제)**: **최소 12자** → 미달 시 설정 거부.
- **아주 흔한 비번 차단**: `password`, `123456` 등 소량의 내장 차단목록에 걸리면 거부.
- **상한**: 넉넉히(예: 128자) — 외우기 쉬운 **패스프레이즈** 허용.
- 설정 화면에 **길이 기반 강도 막대**(참고용)를 표시.
- 비밀번호 생성기의 **패스프레이즈 모드**로 강하면서 외우기 쉬운 마스터 비번을 유도.
- **비밀번호 힌트 기능은 두지 않음** — 힌트가 곧 공격 단서가 되고, 복구불가 원칙과 상충.

### 5.7 마스터 비밀번호 복구 — 복구 키 (TD-010)

> **쉬운 말**: 마스터 비밀번호는 이 앱의 유일한 열쇠라, 잊으면 원칙적으로 금고를 열 수 없다.
> 그래서 최초 설정 때 **비상용 열쇠(복구 키)**를 하나 만들어, 종이 등 **오프라인에 보관**하게 한다.
> 나중에 비번을 잊으면 이 복구 키로 금고를 열고 새 비번을 정한다.

- **동작 원리**: 데이터키(DEK)를 마스터키뿐 아니라 **복구 키로도 감싸** 헤더에 함께 저장(5.2·5.3).
  마스터 비번을 잊어도 복구 키로 DEK를 풀 수 있다.
- **발급 정책**: 복구 키는 **최초 설정 때 무조건 발급**한다. 건너뛸 수 없다.
  - 화면에 복구 키(예: `K7F2-9QX4-…` 형태)와 QR을 함께 표시.
  - **"안전한 곳에 보관했다" 확인 체크**를 받아야 다음 단계로 진행(체크 없이는 완료 불가).
  - 앱은 복구 키를 **평문으로 저장하지 않는다**(저장하면 복구 키의 의미가 사라짐).
  - **복사 버튼 제공(TD-043)**: 손으로 옮겨 적다 틀리는 것이 더 큰 위험이라, 비밀번호와 동일하게
    **클립보드 자동 삭제**를 걸어 복사를 허용한다. 파일로 내보내기는 평문이 디스크에 남아 제공하지 않는다.
- **복구 흐름**:
  ```
  로그인 화면 → [비밀번호를 잊으셨나요?]
     → 복구 키 입력
     → 복구 키로 DEK 언래핑 성공
     → 새 마스터 비밀번호 설정 (→ 마스터키로 DEK 재래핑)
  ```
- **한계 (반드시 고지)**: **마스터 비번과 복구 키를 둘 다 잃으면 복구 불가.** (백도어를 두지 않는 대가)
- 서버·이메일·폰에 의존하지 않아 **로컬 전용 원칙을 유지**한다. OTP·이메일이 복구 수단이 될 수 없는 이유는 TD-010 참고.

## 6. 데이터 모델

암호화되어 `vault.dat` 본문에 직렬화되는 JSON 구조(개념).

```jsonc
{
  "version": 3,                             // v3: 즐겨찾기·최근 사용·휴지통 (v1·v2는 자동 마이그레이션)
  "appTotpSecret": "…(암호화)…",            // 앱 잠금해제용 2FA (미등록이면 생략)
  "sortOrder": "Name",                      // 목록 정렬: Name | RecentlyChanged | RecentlyUsed — TD-040
  "networkAllowed": false,                  // 전역 오프라인 스위치 (기본 차단=false) — TD-013
  "slack": {                                // 슬랙 알림 (옵트인, 기본 OFF) — TD-012
    "enabled": false,
    "webhookUrl": "…(암호화)…",
    "notifyUnlock": true,                   // 잠금 해제 성공
    "notifyLoginFailure": true,             // 로그인 실패
    "notifyPasswordChange": true,           // 비번 추가·변경
    "notifySensitive": false,               // (선택) 마스터 변경·복구 키 사용
    "includeSiteName": false,               // 사이트명 노출 기본 OFF
    "messageTemplate": "🔓 {이벤트} · {시각}", // 변수 템플릿 (허용 변수만 치환) — TD-014
    "deviceName": null                      // {기기명} 변수용 (선택)
  },
  "entries": [
    {
      "id": "uuid",
      "title": "예: Steam",                  // 사이트/게임 이름
      "url": "https://…",
      "login": "myid 또는 my@email.com",      // 문자/이메일 겸용 (형식 구분 없음)
      "password": "…(항목 단위 암호화, 지연 복호화)…",
      "notes": "메모",
      "tags": ["게임", "메인"],               // 자유 태그 (계정 구분·분류·필터, 여러 개 가능) — TD-011
      "createdAt": "2026-07-29T13:00:00Z",   // ISO 8601 (UTC)
      "updatedAt": "2026-07-29T13:00:00Z",
      "lastChangedAt": "2026-07-29T13:00:00Z", // 마지막으로 비밀번호를 바꾼 시각
      "passwordHistory": [
        { "password": "…", "changedAt": "2026-04-01T09:00:00Z" }
      ],
      "totpSecret": "…(암호화, 선택)…",       // 사이트별 2FA (선택)
      "isPinned": false,                     // 즐겨찾기 고정 — TD-040
      "lastUsedAt": null,                    // 마지막 OTP 인증 시각 (미사용이면 null) — TD-040
      "deletedAt": null                      // 휴지통에 들어간 시각 (null이면 활성) — TD-041
    }
  ]
}
```

- **한 사이트에 여러 계정**: 같은 사이트의 여러 계정은 각각 독립 `entry`로 저장한다
  (같은 `title`/`url` 중복 허용). 목록에서는 **사이트명 기준으로 그룹핑**해 표시하고,
  같은 사이트 내 계정은 **태그**(예: `메인`/`부캐`)로 구분한다. (TD-003·TD-011)
- **태그(`tags`) (TD-011)**: 고정 분류(category) 대신 **자유 태그**로 계정을 분류·구분한다.
  한 계정에 여러 태그 가능하며, 검색·필터의 기준이 된다(7.3). `login`은 문자/이메일을 한 칸에서 겸용한다.
- **항목별 개별 암호화 + 지연 복호화 (TD-004)**: 민감 값(`password`, `totpSecret`)은 볼트 전체
  암호화에 더해, **항목 단위로 데이터키(DEK)로 한 번 더 암호화**해 둔다. 목록·상세를 볼 때는 풀지 않고,
  "보기"로 OTP를 통과한 그 순간에만 복호화한다 → 평소 메모리 노출 최소화.
- `lastChangedAt`은 비밀번호를 변경할 때마다 갱신하며, 상세 화면에 "마지막 변경일"로 표시한다.
  (만료 주기·자동 알림은 두지 않음 — TD-002)
- `passwordHistory`는 무한히 쌓이지 않도록 **보관 개수 상한**(예: 최근 N개)을 둔다.
- **즐겨찾기 (`isPinned`, TD-040)**: 켜면 목록 맨 위 "즐겨찾기" 그룹에 **바로가기로** 나타난다.
  원래 사이트 그룹에도 그대로 남으며, 즐겨찾기 그룹의 행에는 사이트명이 함께 표시된다.
- **최근 사용 (`lastUsedAt`, TD-040)**: **OTP 인증을 통과한 시점**에 찍는다. "최근 사용순" 정렬의 기준.
- **휴지통 (`deletedAt`, TD-041)**: 삭제는 이 값을 찍는 **소프트 삭제**다. 값이 있으면 목록·검색·
  내보내기에서 모두 빠지며, **30일**이 지나면 잠금 해제 시 자동으로 영구 삭제된다.
  - `isPinned`·`lastUsedAt`·`deletedAt`은 **앱이 권한을 갖는 필드**라, 항목 수정 시 편집 폼 값이 아니라
    기존 항목 값을 이어받는다(`CreatedAt`·`passwordHistory`와 동일 — TD-021·TD-040).
- **version**: 저장 형식이 바뀌면 올리며, 로드 시 마이그레이션 기준이 된다(5.3·TD-008).

## 7. 주요 기능

### 7.1 계정 관리 (CRUD)
- 추가/편집/삭제. 필드: 사이트명·URL·아이디(문자/이메일 겸용)·비밀번호·메모·태그.
- **사이트명 자동 채움 (TD-046)**: 사이트명 칸은 편집 가능 드롭다운이다. 볼트에 이미 있는
  사이트명(중복 제거·이름순, 휴지통 제외)을 후보로 보여주고, 고르면 그 사이트의 **URL·태그**를
  함께 채운다. 같은 사이트명 항목이 여럿이면 **가장 최근 수정된 항목**이 기준이며,
  사용자가 이미 입력한 값은 지우지 않는다(URL은 비어 있을 때만, 태그는 없는 것만 추가).
  목록에 없는 사이트는 그대로 타이핑해 직접 입력한다. **타이핑 중 자동완성은 없다** — URL·태그를
  끌어오는 것은 드롭다운에서 직접 고른 경우뿐이다.
- **비밀번호 생성기**: 새 항목 추가·비밀번호 변경 화면에서 바로 생성해 채울 수 있다.
  - 길이 조절 (8~64자)
  - 문자 종류 토글 (대문자 / 소문자 / 숫자 / 기호)
  - 혼동 문자 제외 (`0`/`O`, `l`/`1` 등)
  - 생성 강도 표시 (약함 / 보통 / 강함)
  - (선택) 패스프레이즈 모드 — 단어 조합(외우기 쉬운 형태)
  - 난수는 `RandomNumberGenerator`(CSPRNG)로 생성해 예측 불가능성 보장.
- **비밀번호 보기 (TD-047)**: 입력칸의 👁 버튼으로 지금 친 비밀번호를 평문 확인할 수 있다(수동 토글).
  기존 항목을 편집할 때 보이는 고정 10자리 자리표시(TD-026) 상태에서는 버튼이 감춰지며,
  저장된 기존 비밀번호를 보는 경로는 목록의 OTP 게이트 보기 화면 하나로 유지한다.

### 7.2 비밀번호 이력 & 마지막 변경일 (R3)
- 비밀번호를 변경하면 이전 값을 `passwordHistory`에 자동 적재하고 `lastChangedAt`을 갱신.
- 항목 상세에서 **마지막 변경일**과 **과거 비밀번호 이력**을 조회(열람 시에도 OTP 요구).
- 이력은 **최근 N개**까지만 보관(상한 초과 시 오래된 것부터 제거).
- 자동 만료 알림은 없음 — 사이트 접속 시 사용자가 마지막 변경일을 보고 직접 판단.

### 7.3 검색·필터·정렬 (R6)
- 제목/아이디/태그 실시간 검색.
- **태그별 필터**(고정 분류 대신 자유 태그 기준 — TD-011).
- **즐겨찾기(TD-040)**: 계정 단위로 고정하면 맨 위 "즐겨찾기" 그룹에 바로가기가 생긴다(원래 자리에도 유지).
  정렬과 무관하게 항상 최상단.
- **정렬(TD-040)**: 이름순(기본) · 최근 변경순 · 최근 사용순. 고른 값은 볼트에 저장돼 다음 실행에도 유지된다.

### 7.3.1 휴지통 (TD-041)
- 삭제는 **소프트 삭제** — 항목을 휴지통으로 옮기고 **30일** 뒤 잠금 해제 시 자동으로 영구 삭제한다.
- 설정 > 백업·데이터의 **휴지통** 화면에서 **복원 / 영구 삭제 / 비우기**.
- 복원·영구삭제는 비밀번호를 노출하지 않아 **OTP 게이트를 거치지 않는다**. 대신 되돌릴 수 없는
  동작(영구삭제·비우기)만 확인 다이얼로그를 받는다.

### 7.4 OTP 2FA (R5)
- 앱 잠금해제 2FA 등록/재설정(마스터 비번으로 재설정 — TD-005).
- 비밀번호 열람 시 OTP 검증 게이트 → 통과 순간에만 지연 복호화(TD-004).
- (선택) 사이트별 OTP 코드 생성.

### 7.5 마스터 비밀번호 변경 (rekey, TD-006)
- 현재 마스터 비번 확인 → 새 마스터 비번 입력 → **데이터키(DEK)를 새 마스터키로 다시 감싸** 저장.
- 볼트 본문(데이터)은 재암호화하지 않으므로 빠르고 안전(원자적 쓰기 그대로 적용).
- 같은 방식으로, 로그인 시 저장된 **KDF 파라미터가 현재 권장치보다 낮으면 자동으로 상향**해 재저장.

### 7.6 마스터 비밀번호 복구 (복구 키, TD-010)
- 최초 설정 시 **복구 키 무조건 발급** + "안전 보관 확인" 체크(5.7).
- 로그인 화면의 "비밀번호를 잊으셨나요?" → 복구 키 입력 → 새 마스터 비번 설정.
- (선택) 설정에서 **복구 키 재발급**(현재 마스터 비번 확인 후 새 복구 키로 교체).

### 7.6.1 전체 데이터 초기화 (TD-044)

마스터 비밀번호와 복구 키를 **둘 다** 잃으면 볼트를 되살릴 수 없다. 이때 처음부터 다시 시작할 수 있도록
초기화 수단을 둔다. 되돌릴 수 없으므로 진입과 확인을 모두 좁힌다.

- **진입**: 언락 화면의 **비밀번호 칸에 `/reset` 입력** 후 잠금 해제. 화면에 버튼·링크는 두지 않는다.
  - 설정(S7)에 두지 않는 이유: 그 화면은 **잠금을 해제해야** 들어갈 수 있어 정작 필요한 순간에 닿지 못한다.
  - 마스터 비밀번호는 최소 12자(5.6)라 6자인 이 커맨드와 **구조적으로 충돌하지 않는다**.
  - **재시도 잠금(TD-024)보다 먼저** 처리해, 비번을 여러 번 틀려 잠긴 상태에서도 초기화할 수 있다.
- **확인**: 경고창 1회. 취소하면 아무것도 지우지 않는다.
- **삭제 대상**: `vault.dat` · `.tmp` · `.bak` · `.lockout` · `slack-failures.log` (첫 설치 상태로 복귀).
- 삭제 전에 세션을 닫아 메모리의 키·평문을 먼저 버린다(5.5).

### 7.7 백업·가져오기/내보내기
- 암호화 볼트 파일 수동 백업/복원.
- 내보내기는 **항상 암호화 상태**다. 평문 CSV 내보내기·가져오기는 제공하지 않는다(TD-050).
- **잠긴 내보내기 (`.pmexport`, TD-050)**: 유일한 내보내기 경로. 항목 CSV를 **복구 키로 AES-256-GCM 봉인**해
  파일 하나가 새도 내용이 노출되지 않는다.
  - 복구 키는 256-bit 랜덤이라 KDF 없이 그대로 키로 쓴다(복구 래핑과 동일 — TD-010).
  - **봉인 전 키를 검증**한다(헤더의 `dekByRecovery` 언래핑). 틀린 키로 잠그면 영영 못 열기 때문.
  - 파일 구조: `magic(8) + nonce(12) + tag(16) + ciphertext`. magic은 AEAD 연관 데이터로도 쓴다.
  - **그 파일을 봉인한 복구 키로만** 열린다. 복구 키를 재발급해도(TD-035) 옛 파일은 옛 키로 열리며,
    다른 볼트로 항목만 옮길 때도 쓸 수 있다.
  - 백업과의 차이: 백업은 *볼트 파일의 복제*(그 시점 마스터 비번), 잠긴 내보내기는 *항목 데이터의 사본*
    (마스터 비번을 잊어도 복구 키로 열림).

### 7.8 슬랙 알림 연동 (옵트인, 기본 OFF — TD-012)

> **쉬운 말**: "내가 없을 때 누가 금고를 열었는지"를 **폰(슬랙)으로 알아채기** 위한 방어용 알림.
> 로컬 전용 원칙의 **유일한 의도적 예외**이며, 밖으로 나가는 건 짧은 알림 문구뿐 — 비밀번호는 안 나간다.

- **방식**: Slack **Incoming Webhook**. 사용자가 슬랙에서 발급한 Webhook URL을 앱에 등록하면,
  앱이 그 URL로 알림 메시지를 보낸다(HTTPS).
- **URL 저장**: Webhook URL은 **볼트 안에 암호화 저장**(다른 secret과 동일 취급).
- **기본 OFF**: 설정에서 켜야만 동작. 켜기 전에는 어떤 네트워크 통신도 없음.
- **알림 이벤트(각각 on/off 토글)**:
  - 잠금 해제 성공
  - 마스터 비밀번호 로그인 실패(예: 연속 N회)
  - 비밀번호 추가/변경
  - (선택) 마스터 비번 변경·복구 키 사용 등 민감 이벤트
- **전송 내용(민감정보 배제 원칙)**:
  - **절대 미포함**: 비밀번호·아이디·복구 키·Webhook URL 등 모든 secret.
  - **기본 미포함**: **사이트명**(어떤 서비스를 쓰는지 노출되므로 기본 OFF, 원하면 켜기).
  - 포함: 이벤트 종류·시각·(선택) 기기명. 예: `🔓 볼트 잠금 해제됨 · 2026-07-29 14:03`.
- **메시지 폼 수정 — 변수 템플릿 (TD-014)**:
  - 문구를 사용자가 편집하되, **허용 변수만** 끼워 넣는 템플릿 방식. 예: `🔓 {이벤트} · {시각}`.
  - **허용 변수**: `{이벤트}`(이벤트 종류), `{시각}`, `{기기명}`. secret은 **변수 자체를 제공하지 않아** 구조적으로 유출 불가.
  - 화이트리스트 외 토큰(`{…}`)은 치환하지 않고 **리터럴 그대로** 출력 → 우회 차단.
  - 저장 전 **미리보기** 제공, **기본 템플릿 복원** 버튼 제공.
- **전역 오프라인 스위치 종속 (TD-013)**: 슬랙은 전역 스위치의 하위. **전역이 차단이면 슬랙은 동작하지 않는다**(7.9).
- **신뢰성**: **비동기·베스트에포트**. 네트워크 실패·슬랙 장애가 있어도 **앱 동작(잠금 해제·저장)은
  절대 막지 않는다**. 실패는 로컬 로그만 남기고 조용히 넘어간다(가벼운 재시도 1회까지).
  - **로컬 로그도 secret 배제**: 로그엔 비밀번호·아이디·복구 키·Webhook URL 등을 남기지 않고,
    **이벤트 종류·시각·실패 사유**만 기록한다(전송 문구와 동일한 배제 원칙).
- **보안 주의**: 아웃바운드 연결은 "이 시각에 앱을 썼다"는 **메타데이터**를 남긴다(내용은 비어도).
  Webhook URL 유출 시 해당 채널에 스팸이 가능하므로 URL은 암호화 보관·노출 최소화.

### 7.9 설정 모듈 (S7)

부가 설정을 한 화면(설정, S7)에 **섹션으로 묶어** 필요 시 활용한다. 되돌리기 어렵거나 위험한 동작
(마스터 비번/복구 키 변경, 평문 내보내기)은 **확인 다이얼로그**를 거친다(design 5.5·ui 2장).

| 섹션 | 항목 | 근거 |
|---|---|---|
| **보안·계정** | 마스터 비밀번호 변경(rekey), 복구 키 재발급, OTP 재설정, 자동잠금 시간, 클립보드 삭제 시간 | 7.5·7.6·5.4·5.5 |
| **알림(슬랙)** | on/off, Webhook URL 등록, 이벤트 토글, 사이트명 포함 토글, **메시지 폼(변수 템플릿) 수정** | 7.8·TD-012·TD-014 |
| **네트워크** | **전역 오프라인 스위치**(기본 ON=차단) | TD-013 |
| **백업·데이터** | 볼트 백업/복원, 가져오기/내보내기(평문은 경고), **휴지통**(복원·영구삭제·비우기) | 7.7·7.3.1 |
| **정보** | 앱 버전, 볼트 파일 위치 | — |

- **전역 오프라인 스위치(네트워크 섹션, TD-013)**: 모든 아웃바운드의 상위 차단기. **기본 차단**이며,
  차단 상태에서는 **알림(슬랙) 섹션이 비활성(회색)** 처리된다. 슬랙을 쓰려면 전역 스위치를 먼저 해제한다(2단).
- **메시지 폼 수정(알림 섹션, TD-014)**: 허용 변수만 끼워 넣는 템플릿 편집 + 미리보기 + 기본값 복원(7.8).
- 설정 모듈은 **새 부가 기능의 편입 지점**이다 — 이후 네트워크·알림·데이터 관련 옵션이 늘면 해당 섹션에 담는다.

## 12. 테스트 전략 (TDD)

`CLAUDE.md`의 TDD 규칙에 따라 핵심 로직은 **테스트를 먼저** 작성한다(Red → Green → Refactor).
최소한 아래는 단위 테스트로 반드시 검증한다.

- **암호화 라운드트립**: 평문 → 암호화 → 복호화 시 원본 일치. **잘못된 키/변조 데이터는 복호화 실패**.
- **키 래핑/언래핑 (2단 키)**: DEK를 KEK로 감싸고 다시 푸는 왕복. **마스터 비번 변경(rekey) 후에도 기존 데이터가 정상 복호화**.
- **복구 키 (TD-010)**: 복구 키로 DEK 언래핑 → 새 마스터 비번 설정 후에도 **마스터·복구 두 경로 모두로 정상 복호화**. 잘못된 복구 키는 실패.
- **KDF**: 같은 (비번+salt)이면 같은 키, salt가 다르면 다른 키. 파라미터 상향 후 재파생 검증.
- **TOTP**: 시간을 고정한 상태에서 코드 검증, **앞뒤 오차(±30초) 허용**, 만료된 코드 거부.
- **비밀번호 이력**: 변경 시 이전 값 적재, **상한 초과 시 오래된 것부터 제거**, `lastChangedAt` 갱신.
- **버전 마이그레이션**: 옛 버전 파일을 읽어 새 구조로 변환.
- **원자적 쓰기**: 쓰기 도중 실패해도 기존 `vault.dat`이 온전히 남는지.
- **복호화 실패 원인 구분**: DEK 언래핑 실패(비번 오류) vs 본문 태그 실패(파일 손상)를 다르게 판별.

## 13. 보안 주의사항 & 한계

- **마스터 비밀번호를 잊으면 복구 키로 재설정**할 수 있으나(TD-010), **마스터 비번과 복구 키를 둘 다 잃으면 복구 불가**. (백도어를 두지 않는 것이 곧 보안) → 사용자에게 명확히 고지.
- **복구 키는 앱 밖(종이 등 오프라인)에 보관**해야 의미가 있다. 앱·PC 안에 평문으로 두면 사실상 백도어가 된다.
- **개별 열람 OTP는 암호학적 잠금이 아니라 재확인 게이트**다(TD-004). 마스터 비번이 뚫리면 OTP는 방벽이 아님 — 지연 복호화로 노출 시간만 줄인다.
- OTP는 마스터 비번으로 재설정 가능(TD-005) → 즉 OTP의 안전성은 결국 마스터 비번에 종속된다.
- WPF/.NET 환경에서 메모리 상 평문을 100% 제거하기는 어렵다(가비지 컬렉션). 노출 시간을 최소화하는 것이 현실적 목표.
- 로컬 전용이므로 이 PC의 OS 계정 보안(디스크 암호화 BitLocker 등)이 1차 방어선이 된다.

## 14. 향후 확장 여지
